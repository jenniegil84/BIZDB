# MD_ROUTER.md --- 사업센터 대시보드 문서 선택 규칙

-   목적: 사용자의 요청을 먼저 분석한 뒤, 현재 작업에 필요한 MD 파일만
    선택해서 읽는다.
-   원칙: 문서를 전부 읽지 않는다. 필요한 문서만 선택하고, 선택 이유를
    먼저 밝힌 뒤 작업한다.
-   이 문서는 정책·데이터 정의 자체를 담지 않는다. 어떤 문서를 읽어야
    하는지 결정하는 라우터 역할만 한다.
-   저장소 루트에 이 프로젝트 문서들보다 위에 있는 문서 2개가 더 있다 —
    `../USER_OPERATING_MANUAL.md`(사용자 본인에 대한 공통 지침, 모든 문서 중 최상위)와
    `../CLAUDE.md`(저장소 전체 공통 작업 지침). 이 라우터는 아래 프로젝트 전용 문서
    선택만 다루므로 그 두 문서는 목록에 넣지 않았다 — 항상 먼저 적용된다고 가정한다.

------------------------------------------------------------------------

## 1. 사용 가능한 MD 파일

### 0) `PROJECT_CONTEXT.md` (2026-09-07 신설)

**역할:** 이 프로젝트의 현재 상태·기획 의도·주요 의사결정·미정 사항을 계속 쌓는
살아있는 맥락 문서. `CLAUDE.md`가 "어떻게 일할지"(작업 규칙)라면, 이 문서는
"지금 무엇을·왜 그렇게 했는지"(상태·이력·결정)를 담는다.

다음 내용이 포함되어 있다. - 프로젝트 기본 정보·현재 핵심 방향 - 현재 구현
상태(완료/진행 중/미착수) - 데이터 구조·출처 요약(정책/데이터 문서로의
안내) - 주요 의사결정 기록(문제·검토한 안·결정·이유) - 변경 이력(버전별
상세, 기존 CLAUDE.md "업데이트 이력"이 이곳으로 이관됨) - 현재 문제/이슈·
미정 사항·다음 액션 - 배운 점(기존 CLAUDE.md "9. 실수 기록"이 이곳으로
이관됨, 33개 항목)

**선택 기준** - 새 세션·오랜만의 작업 등 "지금 프로젝트가 어디까지 왔는지"
파악이 필요할 때 가장 먼저 훑어본다("1. 프로젝트 기본 정보"~"3. 현재 구현
상태"만이라도). - 과거 결정 배경이 궁금하거나("왜 이렇게 돼 있지?") 비슷한
버그를 다시 만났을 때는 "7. 주요 의사결정 기록"·"13. 배운 점"에서 관련
키워드를 찾는다. - 작업을 마치고 나면 **반드시** "8. 변경 이력"에 한 줄
추가하고, 결정 성격이 강했으면 "7. 주요 의사결정 기록"에도 기록한다(끝나는
문서가 아니라 계속 쌓는 문서). - 실수를 했으면 "13. 배운 점"에 번호를 이어
추가한다.

### 1) `CLAUDE.md`

**역할:** 사업센터 대시보드의 최상위 작업 규칙 (2026-09-07부터 순수 작업
규칙만 담음 — 변경 이력·실수 기록은 `PROJECT_CONTEXT.md`로 이관)

다음 내용이 포함되어 있다. - 사용자 업무 맥락 - 핵심 작업 원칙 - 출력
규칙 - 화면설계 규칙 - 데이터 분석 규칙 - 완료 전 체크리스트 - 코드/구조
유지 원칙 - 사업센터 대시보드 작업 규칙

**선택 기준** - 사업센터 대시보드와 관련된 작업이면 기본적으로
적용한다. - 특히 코드 수정, 화면 수정, 구조 변경, QA 전에는 관련 규칙을
확인한다(과거 실수 기록은 `PROJECT_CONTEXT.md` "13. 배운 점" 참고). - 단, 파일
전체를 무조건 읽지 않는다. 현재 요청과 관련된 섹션만 최소 범위로 읽는다.

------------------------------------------------------------------------

### 2) `CODE_MAP.md` (2026-09-08 신설)

**역할:** `index.html`(한 파일에 전체 기능이 들어있음)에서 어떤 화면을 고치려면 어느
함수를 찾아야 하는지 알려주는 코드 위치 지도. 정책·데이터 문서가 아니라 **코드 구조
전용** 안내다.

다음 내용이 포함되어 있다. - 사이드바 메뉴별 담당 함수(화면마다 IX 시스템 / 영업
어댑터 / 단순 화면 3가지 중 어느 방식인지) - 저장·복원 두 계층(STATE_MAP/BOARD_STATE_MAP)
요약 - 알려진 함정(같은 이름의 죽은 코드·중복 구현 등)

**선택 기준** - 코드 수정(화면 수정·기능 개발·리팩터링) 작업이면 실제로 코드를 열기
**전**에 먼저 확인해, 고칠 함수 위치를 grep으로 헤매는 시간을 줄인다. - 정책 판단이나
데이터 출처 확인에는 쓸모없다(3~5번 문서로 갈 것). - **화면이 다른 함수로 옮겨가는
수정을 했으면 반드시 이 문서도 함께 갱신한다** — CLAUDE.md 8번 섹션 참고.

------------------------------------------------------------------------

### 3) `사업센터_정책정리_*.md`

**역할:** 사용자가 확정한 정책과 판정 기준의 원천

다음과 같은 작업에서 선택한다. - 실적 기준 변경 또는 확인 - 유입경로 /
가입채널 / 최종실적 판정 - 실적보호업체 / 실적보호기간 - 집계 기준 -
기준일 - 플러스 가입 / 플러스 전환 - 요금제 변경 - 신규가입 / 재가입 /
정지 / 정지해제 / 해지 - 화면에 적용되는 업무 정책 - 기존 정책과 사용자
요청이 충돌하는지 확인해야 하는 작업

**질문 예시** - "플러스 전환 기준 바꿔줘" - "위멤버스 실적은 어떻게
잡혀?" - "요금제 변경을 실적으로 포함해" - "이 화면의 실적 기준이 맞아?"

------------------------------------------------------------------------

### 4) `사업센터_데이터출처_정리_*.md`

**역할:** 화면의 값이 어디에서 오고 어떻게 계산되는지 확인

다음과 같은 작업에서 선택한다. - 특정 숫자의 데이터 출처 확인 - Excel /
Flow / 고객마스터 / Supabase 등 원천 확인 - 특정 카드·표·차트가 어떤
함수 또는 데이터에서 만들어지는지 확인 - 하드코딩 값을 실제 데이터로
연결 - 화면과 실제 데이터 연결 수정 - 저장/복원 구조 확인 - 데이터가
없을 때 표시 방식 확인

**질문 예시** - "이 카드 숫자 어디서 가져와?" - "이 값을 실데이터로
바꿔줘" - "하드코딩 없애줘" - "이 화면 Supabase 데이터로 연결해" -
"주간회의 숫자는 어디서 계산돼?"

------------------------------------------------------------------------

### 5) `사업센터_데이터정합규칙_*.md`

**역할:** 서로 관련된 숫자와 화면이 일치하는지 검사 — **0-1장에 「집계 기준 한눈에 보기」
표**가 있다(지표별 잣대·판정 규칙·2026 검산값·보이는 화면). 「이 숫자 왜 달라?」류 질문은
그 표부터 본다.

다음과 같은 작업에서 선택한다. - 숫자 오류 수정 - 카드와 상세 목록
숫자가 다른 문제 - 화면별 동일 지표가 다른 문제 - 집계 함수 수정 -
데이터 매칭 수정 - 기간/기준일 수정 - 실적 계산 수정 - 데이터 관련 개발
완료 후 QA - 배포 전 데이터 검증

**질문 예시** - "카드는 28인데 상세는 왜 27이야?" - "월별과 통합현황
숫자가 달라" - "이 수정 때문에 다른 화면 숫자 깨지는지 확인해" - "데이터
정합성 QA 해줘"

## 2. 문서 선택 순서

사용자 요청을 받으면 아래 순서로 판단한다.

### STEP 1. 작업 영역을 분류한다

현재 요청이 다음 중 어디에 해당하는지 먼저 판단한다.

-   일반 화면/UI 수정
-   기능 개발
-   정책 변경
-   데이터 출처/연결
-   데이터 계산/집계
-   데이터 오류
-   리팩터링/코드 정리
-   QA
-   배포

한 요청이 여러 영역에 해당할 수 있다.

------------------------------------------------------------------------

### STEP 2. 필요한 MD 파일을 선택한다

  -----------------------------------------------------------------------
  작업 유형                           읽을 문서
  ----------------------------------- -----------------------------------
  일반 화면/UI 수정                   `CLAUDE.md` 관련 규칙 + `CODE_MAP.md`(담당 함수 위치)

  기능 개발                           `CLAUDE.md` + `CODE_MAP.md` + 기능과 관련된 문서

  정책 확인/변경                      `CLAUDE.md` +
                                      `사업센터_정책정리_*.md`

  데이터 출처 확인                    `CLAUDE.md` +
                                      `사업센터_데이터출처_정리_*.md`

  하드코딩 → 실데이터                 `CLAUDE.md` +
                                      `사업센터_데이터출처_정리_*.md`

  데이터 계산/집계 수정               `CLAUDE.md` +
                                      `사업센터_정책정리_*.md` +
                                      `사업센터_데이터출처_정리_*.md` +
                                      `사업센터_데이터정합규칙_*.md`

  숫자 불일치/데이터 오류             `CLAUDE.md` +
                                      `사업센터_데이터출처_정리_*.md` +
                                      `사업센터_데이터정합규칙_*.md`,

                                      `사업센터_정책정리_*.md` 추가

                                      `사업센터_데이터정합규칙_*.md`,

                                      문서. 데이터 수정이면
                                      `사업센터_데이터정합규칙_*.md` 필수

## 3. 복합 작업 선택 규칙

작업이 여러 영역에 걸치면 문서를 합쳐서 선택한다.

### 예시 1

요청: \> 플러스 전환 카드 숫자가 월별 화면과 다르니까 고쳐줘.

선택: - `CLAUDE.md` - `사업센터_정책정리_*.md` -
`사업센터_데이터출처_정리_*.md` - `사업센터_데이터정합규칙_*.md`

이유: 플러스 전환의 정책 정의 + 현재 데이터 출처 + 화면 간 숫자 정합성을
모두 확인해야 한다.

### 예시 2

요청: \> 버튼 위치만 오른쪽으로 옮겨줘.

선택: - `CLAUDE.md`의 관련 코드/화면 수정 규칙

나머지 데이터 문서는 읽지 않는다.

### 예시 3

요청: \> 하드코딩된 고객 수를 실제 데이터로 바꿔줘.

선택: - `CLAUDE.md` - `사업센터_데이터출처_정리_*.md`

실제 숫자의 정책 정의나 다른 화면과의 정합성까지 영향을 주는 경우에만
정책/정합 문서를 추가한다.

## 4. 실행 규칙

문서를 선택한 뒤 다음 순서로 작업한다.

1.  사용자 요청을 분석한다.
2.  작업 영역을 분류한다.
3.  필요한 MD 파일을 선택한다.
4.  작업 시작 전에 아래 형식으로 짧게 알린다.

> 작업 분류: 데이터 집계 수정\
> 읽을 문서: CLAUDE.md / 정책정리 / 데이터출처 / 데이터정합규칙\
> 이유: 집계 기준과 데이터 출처, 화면 간 숫자 일치 여부를 함께 확인해야
> 함

5.  선택한 문서에서 **현재 요청과 관련된 부분만** 읽는다.
6.  관련 규칙과 현재 코드 구조를 확인한다.
7.  정책·데이터 출처·정합 규칙 사이에 충돌이 있는지 확인한다.
8.  충돌이 없으면 작업한다.
9.  충돌이 있으면 임의로 판단하지 말고 사용자에게 충돌 내용을 먼저
    알린다.
10. 수정 후 현재 작업에 필요한 QA를 수행한다.

------------------------------------------------------------------------

## 5. 최소 읽기 원칙

문서를 선택했다고 해서 파일 전체를 처음부터 끝까지 읽지 않는다.

반드시: 1. 요청의 핵심 키워드를 먼저 찾는다. 2. 관련 섹션의 위치를
찾는다. 3. 필요한 범위만 읽는다. 4. 추가 정보가 필요한 경우에만 범위를
넓힌다.

예: \> "플러스 전환 숫자가 이상해"

처음부터 정책정리 전체를 읽지 않는다.

먼저 다음 키워드를 찾는다. - 플러스 전환 - 공통 집계 함수 - perfStat -
주간 실적 - 정합 규칙의 플러스 항목

그 부분만 읽고 작업한다.

------------------------------------------------------------------------

## 6. 문서 우선순위

문서 내용이 서로 다를 경우 임의로 섞지 않는다.

기본 확인 순서:

1.  사용자의 현재 명시적 요청
2.  저장소 루트 `../USER_OPERATING_MANUAL.md`(사용자 본인에 대한 공통 지침 — 이 프로젝트뿐
    아니라 어떤 작업에도 적용, 아래 모든 문서보다 위)
3.  저장소 루트 `../CLAUDE.md`(저장소 전체 공통 작업 지침)
4.  `CLAUDE.md`(이 프로젝트 전용 작업 규칙)
5.  `PROJECT_CONTEXT.md`의 "6. 중요한 정책"·"7. 주요 의사결정 기록"(최신 확정 기록)
6.  `사업센터_정책정리_*.md`의 최신 확정 정책
7.  `사업센터_데이터출처_정리_*.md`
8.  `사업센터_데이터정합규칙_*.md`
9.  `CODE_MAP.md`(정책·데이터가 아니라 "코드가 실제로 어디 있는지"에 대해서만 우선—
    이 지도와 실제 코드가 어긋나면 항상 코드가 맞다. 어긋난 걸 발견하면 지도를 고친다)
10. 현재 코드

단, 문서의 버전 또는 기준 index.html 버전이 현재 코드보다 오래된 경우
해당 내용을 최신 사실로 단정하지 않는다.

서로 충돌하면: - 어떤 문서와 어떤 문서가 충돌하는지 표시 - 각 문서의
버전/기준 파일 확인 - 사용자에게 확인받기 전 임의로 정책을 새로 만들지
않는다.

------------------------------------------------------------------------

## 7. 파일 버전 선택 규칙

동일 종류의 MD 파일이 여러 개 있으면 파일명 버전이 가장 높은 최신본을
우선한다.

예: - `사업센터_정책정리_v01_42.md` - `사업센터_정책정리_v01_43.md`

→ `v01_43`을 선택한다.

단, 최신 파일 내부에서 특정 섹션이 오래된 코드 기준이라고 명시되어
있으면 그 부분은 그대로 최신 정보라고 가정하지 않는다.

`PROJECT_CONTEXT.md`·`CLAUDE.md`·`CODE_MAP.md`는 이 규칙 대상이 아니다 — 파일명에
버전이 없는 단일 파일로, 계속 그 파일 안에서만 갱신한다(새 버전 파일을 따로 만들지
않는다).

------------------------------------------------------------------------

## 8. 금지 사항

-   모든 MD 파일을 습관적으로 전부 읽지 않는다.
-   파일 이름만 보고 내용을 추측하지 않는다.
-   정책 문서를 확인하지 않고 정책을 새로 만들지 않는다.
-   데이터 출처를 확인하지 않고 숫자 산식을 추측하지 않는다.
-   정합 규칙을 무시하고 한 화면의 숫자만 맞추지 않는다.
-   오래된 MD 내용을 현재 코드보다 무조건 우선하지 않는다.
-   관련 없는 문서를 읽어 컨텍스트를 불필요하게 늘리지 않는다.
-   사용자가 요청하지 않은 기능까지 작업 범위를 확대하지 않는다.

------------------------------------------------------------------------

## 9. 핵심 원칙

> **요청 → 작업 분류 → 필요한 MD 선택 → 관련 부분만 읽기 → 코드 확인 →
> 수정 → 필요한 QA**

MD 파일을 많이 읽는 것이 목적이 아니다.

**현재 작업에 필요한 규칙을 정확히 찾아 적용하는 것이 목적이다.**
