## 1. 실적 판정 규칙 (최종 확정)

### 용어 — 「실적보호업체」와 「실적보호기간」은 다른 말이다

| 용어 | 뜻 | 적용 대상 |
|---|---|---|
| **실적보호업체** | 프로젝트 지침에 등록한 위멤버스 실적보호 명단(사업자등록번호) **34곳** | 그 명단에 든 업체만 |
| **실적보호기간** | 업무등록일 기준 **3개월** 창. 기간 내면 유입채널, 만료면 가입채널로 귀속 | **모든 신청 문의** |

- 실적보호업체는 **기간 개념이 없다** — 가입만 되면 기간과 무관하게 무조건 위멤버스 실적.
- 상세 화면의 「실적보호」 칸은 이 구분을 그대로 보여준다:
  `실적보호업체(기간 무관)` / `D-86 ~2026-11-20 유입채널 귀속` / `만료 · 가입채널 귀속`

### 판정 규칙
1. **실적보호업체는 신청 문의부터 가입까지 모두 위멤버스 실적으로 본다.**
   유입경로·최종실적 모두 `위멤버스 > 온라인 마케팅`. **실적보호기간과 무관하게 무조건** 적용된다.
2. **가입이 아닌 신청 문의 중 실적보호업체를 제외한 나머지는 기본 3개월의 보호기간을 준다.**
   기준일은 **업무등록일**이며, 기간 내면 유입채널, 만료되면 가입채널로 귀속한다.

### 채널 3종

| 구분 | 판정 |
|---|---|
| **유입경로** | 패스코드(PATH_CD) + 내용 유입경로 매핑으로 자동판정, 없으면 수동선택. 단 실적보호업체는 `위멤버스 > 온라인 마케팅` |
| **가입채널** | 플로우 내용의 추천인코드 → 추천정보관리의 추천채널로 자동판정(매핑 없으면 자동지정 안 함), 없으면 수동선택 |
| **최종실적** | ① 수동선택 우선 → ② 실적보호업체면 위멤버스(기간 무관) → ③ 업무등록일 기준 3개월(기간 내=유입채널, 만료=가입채널). 자동판정·수동선택 병행 |

### 집계 모수 — 세 표 모두 **문의 기준**

| 표 | 모수 | 집계 대상 |
|---|---|---|
| 유입경로별 실적 | **전체 문의** | 각 문의의 유입경로 값 |
| 가입채널별 실적 | **가입 문의만** | 각 문의에 가입채널로 지정한 채널 |
| 최종실적별 실적 | **가입 문의만** | 각 문의에 최종실적으로 지정된 채널 |

- **가입 문의** = 문의 유형이 신규가입·재가입인 건(규칙 ③의 "가입이 아닌 신청 문의"와 같은 구분).
- 세 표 모두 값이 문의 자체에 붙어 있으므로, 가입 건과 사업자번호로 잇는 과정은 **불필요하다**.

### 단일 원천 — 「공통 집계 함수」 (확정)

**용어**: 대화·문서에서는 **「공통 집계 함수」** 또는 **「기간 집계」** 라고 부른다(코드명 `perfStat`).

**하는 일**: 시작일·종료일을 받아 그 기간의 실적 8종을 한 번에 계산한다.

```
공통 집계 함수('2026-08-01', '2026-08-31')
  → 도입문의 · 신규가입 · 해지 · 재가입 · 정지 · 요금제변경 · 순증 · 전환율
```

**통합현황 · 실적 분석(일별·주간·월별·누적) · 실적 관리는 모두 이 함수 하나만 쓴다.**
기간만 다르게 넣을 뿐이므로, 같은 기간이면 어느 화면에서 보든 값이 같을 수밖에 없는 구조다.

| 화면 | 넣는 기간 |
|---|---|
| 통합현황 | 이번 달 1일 ~ 기준일 (전월은 그 달 전체) |
| 일별 | 그날 하루 |
| 주간 | 그 주 목~수 |
| 월별 | 그 달 1일 ~ 말일 |
| 누적 | 1900-01-01 ~ 기준일 |
| 실적 관리 | 전체(기간 필터로 조절) |

| 항목 | 함수 |
|---|---|
| 실적 대상 판정(테스트·공지 제외) | `isPerfTarget()` |
| 기간별 집계 | `perfStat(시작일, 종료일)` |

- **화면을 고칠 때는 어느 한쪽만 바꾸지 말고 이 함수를 고친다.** 그래야 구조적으로 어긋나지 않는다.
- 화면끼리 숫자가 다르면 십중팔구 **어느 한 화면이 이 함수를 안 쓰고 따로 계산**하고 있는 것이다.
  (실제 사례: 통합현황이 캐시 집계를 읽고 있었음, 실적 관리에 기간 조건이 빠져 있었음)

### 기준일 (확정)

**기준일 = 플로우 파일과 고객마스터 중 늦은 날짜.**

- 데이터를 불러온 뒤 저장된 데이터에서 실제 최대 날짜를 다시 구해 맞춘다.
  (기준일은 저장되지 않아, 이 재계산이 없으면 새로고침 시 초기값으로 되돌아간다 — 실제로 겪은 문제)
- 기준일이 곧 데이터 최대일이므로, 기준일로 자르는 화면과 자르지 않는 화면의 값이 자연히 같아진다.
- 통합현황 상단에 두 파일이 각각 언제까지 반영됐는지 표시한다 — `(플로우 ~8/29 · 고객 ~8/26)`.
  날짜가 다르면 주황으로 떠서 어느 파일을 다시 받아야 할지 알 수 있다.
  한쪽이 뒤처져 있으면 그 기간의 값이 0으로 나오는데, 그건 오류가 아니라 **데이터가 아직 없는 것**이다.

### 원천 원칙 (확정)

**문의·신청은 플로우, 가입·재가입·정지·정지해제·해지·요금제변경은 마스터파일에서 가져온다.**

- 플로우 문의는 유형이 「재가입」·「신규가입」이든 **구분은 전부 「문의」**로 둔다.
  신청서에 적힌 유형일 뿐 실제 처리 결과가 아니다 — 정지해제인데 플로우에 재가입으로 찍힌 건이
  재가입 실적으로 잡히던 원인이었다. (문의 유형은 「유형·요금제」 칸에 그대로 남는다)
- **정지해제**는 재가입이 아니다. 정지 상태에서 다시 이용을 시작한 별개 이벤트로 따로 센다.
- **정지·정지해제는 순증에 넣지 않는다.** 순증 = `가입 + 재가입 − 해지`.
  서로 상쇄되는 상태 변화라 순증을 흔들지 않는다.

### 실적 대상 (확정)

**테스트·공지는 실적 대상이 아니다.** 실적 관리 목록과 실적 분석(일별·월별·누적)은 **같은 판정 함수**
(`isPerfTarget`)를 쓰므로 두 화면의 모수가 구조적으로 어긋날 수 없다. 제외 조건이 늘면 이 함수 한 곳만
고친다.

|---|---|
| **신청 관리** | 플로우 원본 **조회 전용**. 입력·수정·삭제 기능 없음. 상세 모달도 값 표시만 |
| **실적 관리** (실적 분석 섹션) | 유입경로·가입채널·최종실적 **지정 전용** + 판정 규칙 설정(유입경로 관리·추천 정보 관리) |
| 일별·월별·누적 | 집계 조회 |

- 실적 관리 탭은 미지정 건을 맨 위에 노란 배경으로 올려 남은 작업을 바로 보여준다.
- 상단 카드: 전체 문의 / 지정 필요 / 실적보호업체 / 최종실적 수동 지정.
- 여기서 지정한 값은 일별·월별·누적 집계에 곧바로 반영된다(같은 원천을 쓴다).

### 화면 표시 순서
- 유입경로별 현황 카드: **전체 > 마케팅 > 영업 > 위멤버스 > 세미나 > 컨설팅 > (추가 대분류) > 미분류**
  (미분류는 항상 맨 끝)

### 매칭 기준 (확정)

**모든 매칭은 사업자번호로만 한다. 사무소명 매칭은 쓰지 않는다.**

| 대상 | 매칭 방식 |
|---|---|
| 위멤버스 실적보호 판정 | 실적보호 명단의 사업자번호 ↔ 문의의 사업자번호 |
| 가입 건 ↔ 원본 문의 | 고객마스터의 사업자번호 ↔ 문의의 사업자번호 |

- 비교 시 양쪽 모두 숫자만 남겨 정규화한다(`269-26-01724` = `2692601724`).
- 사무소명 매칭을 쓰지 않는 이유: 명단에 `우일택스` `세움세무회계` 같은 짧은 상호가 있어, 다른 사무소
  문의 제목에 우연히 포함되면 그 건의 실적이 통째로 위멤버스로 잘못 귀속된다.
- 문의 쪽 사업자번호는 플로우 파일의 **'내용' 컬럼**에서 뽑는다. 그 파싱이 들어간 이후(v08.27)
  플로우 파일을 다시 업로드해야 매칭이 붙는다. 매칭 현황은 표 위 진단 문구로 확인할 수 있다.

### 화면 표시 규칙
- 신청 관리 상세 모달의 **최종실적은 항상 드롭다운**이며, 어떤 근거로 판정됐는지 배지로 함께 표시한다.
  - `실적보호 명단 · 기간 무관 확정` / `실적보호기간 내 · 유입채널 귀속` / `실적보호기간 만료 · 가입채널 귀속` / `수동 선택`
- 신청 관리 목록 카드 앞면에 **유입 · 가입 · 최종** 3단계를 점으로 표시한다. 값이 지정됐는지(공란·미분류가
  아닌지)만 보고 켜짐/꺼짐으로 나타낸다.
- 추천인코드가 추천정보관리 표에 매핑돼 있지 않으면 **자동지정하지 않는다.** 화면에는
  `추천 정보 관리에 매핑 없음`으로 표시해 등록이 필요함을 알린다.

### 두괄식 — 모든 보고 내용의 기본 형식 (v01.17 확정)

**결론을 먼저 두고, 근거를 뒤에 둔다.** 화면·문서·회신 어디에나 적용한다.

| 대상 | 적용 방법 |
|---|---|
| **KPI 블록** | 핵심 지표를 큰 카드로 위에 두고, 나머지는 「세부 지표」로 아래에 둔다 |
| **표** | 표 위에 결론 한 줄(전체 건수 · 1위 항목 · 비중)을 먼저 둔다 |
| **목록** | 상위 몇 건만 먼저 보이고 나머지는 「더보기」로 접는다 |
| **분석 블록** | 특이점(판단)을 먼저, 집계 근거를 뒤에 둔다 |
| **채팅 회신·문서** | 결론 → 근거 → 확인 필요 순서. 과정 설명을 앞에 두지 않는다 |

적용 예 — 실적 분석 핵심 KPI 4종(도입문의·순증·플러스 가입·플러스 전환율), 유입경로별 표의
요약 줄, 주간회의 ①-2 인사이트(특이점 먼저 → 근거 카드 뒤), ①-3 목록 5건 + 더보기.

**주의 — 두괄식은 「결론을 앞에 두라」는 뜻이지 「설명을 덧붙이라」는 뜻이 아니다.**
결론 줄에 들어가는 것은 값과 그 값을 이루는 숫자뿐이며, 산출 기준을 설명하는 문장은 넣지
않는다(아래 「카드 안 설명 금지」와 함께 지킨다).

### 카드 안 설명 금지 (v06.96 확정 · v01.17 재확인)

카드·KPI 칸·표 행에는 **라벨 · 값 · 증감 · 그 값을 이루는 항목 목록**만 둔다.
무엇을 어떻게 세는지 설명하는 문장과 툴팁은 넣지 않는다. 산출 기준은 코드 주석에만 남긴다.

- 숫자의 근거를 보여야 하면 **문장이 아니라 목록의 한 줄**로 넣는다.
  예: 「유입경로 미확인 5건」이라고 쓰는 대신 목록에 `미분류 5건` 줄을 둔다 —
  설명 없이도 목록 합계가 총건과 맞아 화면에서 바로 검산된다.

## 1-2. 집계 기준 (확정)

**가입 · 정지 · 해지 · 재가입은 전 구간(일별·월별·누적) 모두 날짜 기준으로 센다.**

| 항목 | 기준 컬럼 |
|---|---|
| 가입 | 가입일 |
| 해지 | 해지일 (+ 현재 상태='해지') |
| 정지 (일별·월별) | 정지일 — 「그 기간에 몇 곳이 정지됐나」 |
| 정지 (누적 요약) | **현재 상태='정지'** — 정지는 되돌아올 수 있어 이력과 현재가 다르다 |
| 재가입 | 재가입일 |
| 순증 | 가입 + 재가입 − 해지 |
| 현재 정상 | **누적가입 − 누적해지 − 누적정지** (검산식으로 산출) |

- **정지 해제는 재가입으로 보지 않는다.** 재가입은 재가입일이 찍힌 건만 센다.
  (정지해지일시는 파싱해 두었으나 어떤 집계에도 쓰지 않는다)

### 실적 지정 대상 (v01.26 확정)

**가입뿐 아니라 요금제 변경도 채널 지정 대상이다.**
베이직·구간요금제에서 플러스로 올라가면 매출이 늘고, 그 건이 어느 채널의 성과인지 따져야 한다.

| 문의 유형(`inqCls`) | 유입경로 | 가입채널·최종실적 |
|---|---|---|
| `join` — 신규가입·재가입 | 지정 | **지정** |
| `plan` — 요금제 변경 (`개업성장패키지_요금변경` 등) | 지정 | **지정** (v01.26 신규) |
| `inq` — 단순 문의·신청 | 지정 | 대상 아님 |
| `notice` · `test` | 대상 아님 | 대상 아님 |

종전에는 `join`만 대상이라 요금제 변경 건은 드롭다운이 잠겨 채널을 넣을 수 없었다.

(v01.27에서 해소 — 요금제 변경도 채널 표 모수에 들어가므로 지정한 값이 집계에 반영된다.)

### 채널 표의 모수 (v01.29 확정 · v01.16·v01.25·v01.27·v01.28 변경)

**가입채널별·최종실적별 표의 모수는 「마스터 파일의 실적 사건 전부」다.**

종전(v01.16)에는 세 표 모두 문의 기준이었고, v01.25에서 가입·재가입만으로 좁혔다가,
요금제 변경도 실적이므로 **마스터 사건 전체**로 확정한다.

| 표 | 모수 | 세는 것 |
|---|---|---|
| 유입경로별 (문의 기준) | 그 기간 도입 문의 전체 | **문의가 어디서 왔나** |
| 가입채널별 (가입 기준) | 마스터의 **신규가입 + 재가입** | **가입이 어느 채널로 잡혔나** |
| 최종실적별 (가입 기준) | 〃 | **최종 귀속이 어디인가** |
| **요금제변경 채널별** (v01.29) | 마스터의 **요금제변경** | **요금제 변경이 어느 채널 성과인가** |

**요금제 변경은 가입과 별도 표로 본다 (v01.29).** 한 표에 섞으면 「가입이 몇 건인지」가 흐려진다.
요금제 변경에는 「가입채널」이라는 개념이 없으므로 **최종실적(귀속 채널) 기준**으로만 본다.

이 표만 **소분류를 「변경 전 → 변경 후」로 둔다 (v01.30).** 요금제 변경은 채널만으로는 판단이 안 된다 —
플러스로 올라간 건과 베이직으로 내려간 건은 매출 방향이 반대다. 대분류(채널)를 펼치면
그 채널에서 어떤 요금제 이동이 있었는지 그대로 보인다.

**요금제 변경 중 실적으로 세지 않는 것** (v01.21 확정 규칙을 그대로 적용)

| 제외 | 이유 |
|---|---|
| 변경 전 = 변경 후 | 시스템 재등록이지 요금제를 바꾼 것이 아니다 |
| 구간요금제 → 베이직 | 구간요금제 폐지에 따른 내부 일괄 전환 |

그 밖의 변경(상향·하향·다른 요금제로 이동)은 고객이 실제로 바꾼 것이라 센다.

**채널값을 찾는 순서**
1. 사업자번호로 원본 문의를 찾아 그 문의의 값(가입채널 / `IX_creditChannel`)을 쓴다
2. 문의가 없으면 「문의 없는 실적」에서 지정한 값(`perf_master`)을 쓴다
3. 둘 다 없으면 **미분류** — 지어내지 않는다

**「문의 없는 실적」에도 실적보호업체를 표시한다 (v01.29).**
실적보호 명단(34곳)은 사업자번호로만 판정하므로 문의가 없어도 그대로 판정된다.
이 업체는 기간과 무관하게 위멤버스로 확정이므로 **드롭다운 대신 확정값을 보여 주고**,
「지정 필요」 건수에서도 뺀다 — 고를 필요가 없는 것을 고르게 두면 잘못 지정된다.

**「문의 없는 실적」 목록도 같은 제외 규칙을 쓴다** — 두 화면의 기준이 갈리면 지정한 건이
집계에 안 잡히거나 그 반대가 된다.

**채널 미지정 건은 두 표에서 뺀다 (v01.28)**
「어느 채널에서 나왔나」를 보는 표인데 미분류가 21건씩 쌓이면 실제 채널 비중이 그 밑에 묻힌다.
뺀 건수는 표 아래에 적어 모수가 왜 줄었는지 알 수 있게 한다.
**유입경로별 표는 미분류를 그대로 둔다** — 그건 「지정이 얼마나 남았나」를 보는 값이라 빼면 안 된다.

**수치 변화 (2026-08)** — 가입채널·최종실적 표 합계
`13건(문의 기준)` → `10건(가입만)` → `32건(마스터 실적 사건)` → **채널이 지정된 건만** 표시

### 채널 요약의 「최다」는 대분류 기준 (v01.41 확정 · v01.17 소분류에서 재변경)

**두괄식 결론 줄(「N건 · OO 최다 M건」)의 「최다」는 대분류(채널) 소계 기준으로 판정한다.**
소분류(세부 경로) 최다가 아니다.

- 이 기준은 이미 **한 번 바뀌었다가 되돌아온 적이 있다** — v08.148에서 대분류로 바꿨다가
  v08.154에서 소분류로 되돌렸고, v08.201에서 **다시 대분류로 확정**했다. 다음에 손댈 때는
  이 이력부터 확인하고, 또 바꾸려면 이 표를 먼저 갱신한다.
- 대분류 기준으로 정한 이유: 소분류 최다는 아래 표(대분류 소계가 큰 순)와 결론이 어긋나
  보일 수 있다 — 예: 마케팅 소계(15건, 소분류 4종)가 위멤버스 소계(7건, 소분류 1종)보다 커도,
  소분류 단위로 비교하면 위멤버스(7건)가 마케팅의 개별 소분류(온라인 마케팅 7건 등)보다 크게
  나와 결론 줄에 위멤버스가 뜬다. 대분류 기준이면 표와 결론이 항상 같은 순서를 가리킨다.
- 적용 범위: 유입경로별·가입채널별·최종실적별·요금제변경 채널별 4개 표 전부 (공통 함수 `perfTbl2` 하나로 계산되므로 자동으로 같이 적용된다).

### 발생 건 목록의 채널 표시는 최종실적 기준 (v01.40 확정)

**일별·월별·누적·주간회의의 「발생 건 목록」에 표시되는 채널값은 최종실적(`IX_creditChannel`)이다.**
유입경로(원본, `IX_inflowResolve`)가 아니다.

- 종전에는 이 목록들이 v06.89부터 원본 유입경로만 보여줬다. 실적 관리 탭과 채널 요약표는
  이미 실적보호·가입채널까지 반영한 최종실적을 쓰고 있어서, **같은 사건인데 화면마다 다른 채널이
  보이는 어긋남**이 있었다(실적 관리에서 위멤버스로 지정한 건이 발생 건 목록에는 다른 유입경로로 표시).
- 최종실적 값이 없으면(계산 함수를 못 찾는 등) 종전의 유입경로로 폴백한다 — 값이 아예 안 보이는
  것보다는 낫다.
- 이 규칙은 **표시(목록 열)에만 적용**된다. 「유입경로별 실적」 표 자체는 여전히 원본 유입경로를
  센다(위 「채널 표의 모수」 참고) — 그건 「어디서 유입됐나」를 보는 값이라 최종실적으로 바꾸면 안 된다.

### 문의 없는 실적도 실적 분석에 들어간다 (v01.39 확정)

**「문의 없는 실적」 목록에서 채널을 지정하면 실적 분석 채널 표에 그대로 반영된다.**
종전에는 그 목록이 **조회만 되고 지정 칸이 없어**, 문의 없이 처리된 건은 채널이 영영 미지정으로 남았다.
실적 분석 쪽은 이미 마스터 사건 전체를 모수로 삼고 있었으나(v01.27), 읽을 값이 만들어지지 않았다.

| | 내용 |
|---|---|
| 지정 위치 | 실적 관리 → 「문의 없는 실적」 탭의 **유입경로** 열 |
| 저장 | `perf_master` · 키는 **`M｜사업자번호｜구분｜일자`** |
| 반영 | 가입채널별·최종실적별·요금제변경 채널별 표 (실적 분석 3탭 공통) |
| 선택지 | 「문의 있는 건」과 **같은 함수**(`inflowOptions`) — 값이 갈리면 집계가 어긋난다 |

- **「플러스 전환」은 화면 표시용 이름**이고 사건은 요금제 변경이므로, 키는 `요금제변경`으로 만든다.
  그래야 실적 분석이 읽는 키와 맞는다.
- **실적보호업체는 드롭다운 대신 확정값**을 보여주고 지정 대상에서 뺀다(기간 무관 위멤버스 — v01.29).
- 미지정 건은 노란 배경으로 표시해 남은 일이 보이게 한다.

### 신청 관리 — 「해지신청」 대신 「고객 현황」 (v01.38 확정)

신청 관리의 2단 서브탭에서 **해지신청을 빼고 고객 현황을 넣는다.**
해지신청은 플로우의 별도 프로젝트라 이 화면(플로우 조회 전용)에서 볼 일이 적었고,
정작 필요한 「그 기간에 무슨 일이 있었나」는 고객 마스터에 있다.

| | 내용 |
|---|---|
| 원천 | 세무사무소목록(`__xlOfficeRows`) |
| 짜임 | 주간회의 ①-3과 같다 — 구분별 칩 → 기본 5줄 → 더보기 |
| 사건 6종 | 신규가입 · 재가입 · 요금제변경 · 정지 · 정지해제 · 해지 |
| 기간 | 이 화면에서 따로 고른다(기본 기준월). **신청 관리의 문의 필터와 별개** — 원천이 다르다 |
| 성격 | **조회 전용.** 지정·수정은 실적 관리에서 한다(신청 관리는 조회 전용 원칙 유지) |

- **해지는 해지일 + 현재 상태='해지'** 인 것만 센다 — 실적 분석과 같은 기준(v01.09).
- 구분별 칩은 **필터 전 전체**로 센다 — 걸러 놓고 세면 다른 구분으로 옮길 수 없다.
- 이 목록에는 **실적 제외 규칙을 적용하지 않는다.** 「무슨 일이 있었나」를 그대로 보는 화면이라
  요금제 변경 27건이 전부 나온다(실적 분석의 22건과 목적이 다르다).
- 해지신청 렌더(`__renderChurnReq`)는 지우지 않고 남겨 둔다 — 되돌릴 수 있게.

### 실적 관리 — 문의 없는 실적 (v01.24 확정)

**실적 관리는 플로우 문의만 모수로 삼는다.** 그런데 가입·재가입·요금제변경은 문의 없이 처리되는
경우가 많아, 그런 건은 목록에 나오지 않고 채널을 지정할 방법도 없었다 — 채널 실적에서 통째로 빠졌다.

(근거: 2026-08 마스터 기준 신규가입 9 · 재가입 1 · 요금제변경 27건 — 문의가 없으면 전부 누락)

**처리 방식 — 같은 화면 아래에 별도 목록(B안)**

| 목록 | 모수 | 하는 일 |
|---|---|---|
| 위 (문의 기준) | 플로우 문의(`isPerfTarget`) | 유입경로·가입채널·최종실적 지정 — 종전과 동일 |
| 아래 (**문의 없는 실적**) | 마스터의 가입·재가입·요금제변경 중 **플로우에 짝이 없는 것** | 유입경로 지정 |

- **짝짓기는 사업자번호로만** 한다(사무소명은 축약·띄어쓰기로 잘못 붙는다 — v01.16 원칙).
  하이픈·공백 유무는 무시한다.
- **사건 종류까지 맞춰** 제외한다 (v01.37). 종전에는 「문의가 하나라도 있는 업체」를 통째로
  뺐는데, 가입 문의만 있고 요금제 변경은 문의 없이 처리된 업체의 변경 건이 **어디에도 안 나왔다**
  (2026-08 기준 3건). 이제 가입 문의가 있으면 그 업체의 **가입 사건만** 빼고, 요금제 변경 사건은 남긴다.
- **기간은 위 필터를 그대로 따른다** — 두 목록의 기준이 갈리면 안 된다.
- 위 목록의 숫자는 건드리지 않는다 — 실적 분석·엑셀 정산의 모수가 흔들리지 않는다.

**지정값 저장** — `perf_master` kind에 따로 저장한다. 문의 기준(`inq_manage`)은 fid를 키로 쓰는데
마스터 사건에는 fid가 없어, 같은 곳에 넣으면 키 체계가 달라 서로를 덮어쓴다.
키는 `M|사업자번호|구분|일자` 형태로 계산해 만든다(같은 사건이면 늘 같은 키가 나온다).

**유입경로 선택지는 위 목록과 같은 함수**(`inflowOptions`)를 쓴다 — 값이 갈리면 집계가 어긋난다.

### 플러스 가입과 플러스 전환은 나눠서 본다 (v01.33 확정 · v01.32 변경)

**핵심 카드의 「플러스 가입」은 신규만 센다.** 플러스 유입 성과를 보는 값이기 때문이다.
(월 목표는 v01.34에서 전환까지 포함하도록 바뀌었다 — 목표와 이 카드는 다른 것을 센다.)

| 지표 | 위치 | 판정 |
|---|---|---|
| **플러스 가입** | 핵심 카드 | 가입일이 그 기간 · **가입 시점 요금제**에 「플러스」 **또는** promo가 개업성장패키지 |
| **플러스 전환** | **핵심 카드** (v01.35) | 요금제 변경일이 그 기간 · 변경 후 플러스 · **변경 전 ≠ 플러스** |

**가입 시점 요금제로 판정한다 (v01.36 확정).**
`이용요금제`는 **현재** 값이라, 베이직으로 가입한 뒤 플러스로 바꾼 곳도 가입으로 잡혔다.
그러면 같은 곳이 「플러스 전환」에도 들어가 두 카드가 한 곳을 각각 센다.

> 요금제 변경일이 **가입일보다 뒤**면 「변경 전 요금제」가 가입 시점 값이다.

이렇게 하면 가입 후 올린 곳은 **전환에서만** 잡혀 두 카드가 겹치지 않는다.
(2026-08 리유세무회계 — 08-28 베이직 가입 → 08-31 플러스 → 전환으로만 집계)

**수치 변화** — 2026-08 플러스 가입 `2건 → 1건`. 다른 달(2026-03~07)은 변동 없다.
두 카드 합이 실제 확보 수와 맞는다: **1 + 13 = 14곳**(겹침 0).

**왜 나누는가 — 두 숫자가 반대로 움직인다**

| 월 | 신규 중 플러스 | 전환 |
|---|---|---|
| 2026-03 | 7 | 1 |
| 2026-04 | 5 | 2 |
| 2026-05 | 2 | 4 |
| 2026-06 | 2 | 0 |
| 2026-07 | **0** | 6 |
| 2026-08 | 2 | **13** |

합쳐 두면 **2026-07처럼 신규가 0건인 달을 놓친다**(합계로는 6건이라 정상으로 보인다).
성과 주체도 다르다 — 신규는 마케팅·영업(유입), 전환은 CS·영업(업셀)이다.
2026-08 전환 13건은 대부분 PREMIUM·구간요금제 폐지에 따른 이동이라 신규 실적과 섞으면
「이번 달 잘했다」로 잘못 읽힌다.

**주간회의에도 같은 정의로 확장 (v01.42 확정)**

**주간회의 「① 주간 실적 요약」에도 플러스 전환을 핵심 카드로 추가한다.** 판정은 위와 완전히
같다(그 주에 요금제 변경일이 있고, 변경 후 플러스·변경 전 ≠ 플러스). 배치는 플러스 가입 바로
오른쪽 — 두 지표가 나란히 있어야 그 주에 확보한 플러스가 신규/전환 어느 쪽에서 왔는지 바로 보인다.

- **요금제 변경 합계에서는 빼지 않는다.** 플러스 가입이 신규가입 안에 이미 포함된 채 별도로도
  보이는 것과 같은 방식 — 이미 집계된 값 중 일부를 다시 보여주는 것이다. 빼 버리면 ①-3
  발생 건 목록(요금제변경 태그를 그대로 쓰는 v07.82 규칙)과 숫자가 어긋난다.
- 월별 정의와 마찬가지로, **「플러스 전환」은 표시용 이름이고 사건 자체는 요금제 변경**이다.

### 월 목표는 전환까지 포함해 센다 (v01.34 확정)

**「신규 가입 30건」 목표의 달성 계산에 플러스 전환도 더한다.**
목표 카드 라벨도 **「신규 가입 + 플러스 전환」**으로 바꿔 무엇을 세는지 드러낸다.

- **겹치는 곳은 한 번만 센다.** 베이직으로 가입한 뒤 같은 달에 플러스로 바꾼 곳은 양쪽에 있다.
  단순히 더하면 한 곳을 두 번 센다.
- 2026-08 = 신규가입 9 + 플러스전환 13 − 중복 1 = **21건** → 30건 목표의 **70%**

**핵심 카드 「플러스 가입」은 신규만 그대로 둔다 (v01.33)** — 목표는 전환까지 보되,
플러스 유입 성과 자체는 신규로 본다. 두 값이 다른 것을 세므로 카드 라벨로 구분한다.

**합계(`plusAll`)는 계산해 둔다** — 겹치는 곳을 제외한 값이며, 합계가 필요해지면 그 값을 쓴다.
(2026-08 = 신규 2 + 전환 13 − 중복 1 = 14건)

### 190만원 프로모션 = 개업성장패키지 (v01.23 확정)

**「190만원 프로모션」의 정식 코드명은 「개업성장패키지」다.**
v04.87에서 코드명을 몰라 `개업세무사 성장지원 패키지`로 추정해 두었던 것을 정정한다.
(도입 문의 유형에도 `개업성장패키지_요금변경`·`_신규문의`·`_기존문의`로 쓰인다.)

| 항목 | 내용 |
|---|---|
| 판정 원천 | **청구대상 고객관리** 파일의 `promo` 필드 |
| 판정 규칙 | 값에 「개업」과 「성장」이 함께 들어가면 이 프로모션으로 본다 (표기 흔들림 대비) |
| 집계 방식 | 원래 요금제(예: 플러스)와 **무관하게** 「190만원 프로모션」으로 재분류 |
| 현재 값 | 정상 398곳 중 4곳 — 플러스 97곳에서 빠져 화면에는 플러스 93곳으로 표시 |

**판정은 `isPromo190()` 한 곳에서만 한다.** 종전에는 같은 문자열이 네 곳에 흩어져 있어,
코드명이 바뀌면 한 곳만 고쳐지고 나머지가 조용히 어긋날 수 있었다.

### 요금제 변경 — 내부 일괄 전환은 실적이 아니다 (v01.21 확정 · v01.22 처리방식 확정)

**「구간요금제 → 베이직」은 구간요금제가 폐지되면서 내부에서 일괄 전환한 건이다.**
고객이 요금제를 바꾼 것이 아니므로 **전환 실적으로 보지 않는다.**

(근거: 2026-08 요금제 변경 57건 중 45건이 이 패턴 — 사용자 확인 2026-09-01)

| 구분 | 뜻 | 실적으로 세나 |
|---|---|---|
| 구간요금제 → 베이직 | 요금제 폐지에 따른 내부 일괄 전환 | **아니오** |
| 플러스 → 다른 요금제 | 플러스 이탈 — 「플러스 해지」로 따로 센다 | 별도 항목 |
| 플러스 → 플러스 | 시스템 일괄 재등록 | **아니오** (변경 전 ≠ 플러스 조건으로 제외) |
| 그 밖의 변경 | 고객이 실제로 바꾼 것 | 예 |

**화면 처리** — 주간 인사이트는 이 패턴이 몰려 있으면 「내부 일괄 전환」이라고 사실로 알리고,
실제 고객 변경이 몇 건인지 함께 적는다. 이미 확인된 건이므로 매주 「확인 필요」로 다시 묻지 않는다.
그 밖의 패턴이 몰리면 종전대로 「확인 필요」로 띄운다 — 새로운 일괄 처리를 놓치지 않기 위함이다.

**집계에서는 빼지 않는다 (v01.22 확정).**
카드·표의 「요금제 변경」 건수에는 내부 일괄 전환분도 **그대로 포함**한다.

| | 이유 |
|---|---|
| **빼지 않는 이유** | 발생 건 목록(①-3)의 줄 수와 카드 숫자가 어긋나면 화면에서 검산이 안 된다. 「요금제 변경 57건」 옆에 목록 57줄이 있어야 대조가 된다. |
| **대신 하는 것** | 주간 인사이트가 「45건은 내부 일괄 전환 · 실제 고객 변경은 12건」이라고 알려준다. 숫자는 그대로 두고 해석을 붙이는 방식이다. |

즉 **집계는 사실 그대로, 판단은 인사이트에서** 한다. 실적 보고에 쓸 숫자가 필요하면
인사이트의 「실제 고객 요금제 변경」 값을 쓴다.

### 정지 구분 — 정지사유 기준 (v01.20 확정 · v01.19 정정)

**v01.19에서 「정지일시 유무로 자발/비자발이 갈린다」고 적었으나, 실제 파일로 확인한 결과 사실이 아니었다.**
정지 191곳 중 정지일시가 없는 건 **1곳**뿐이다. 구분은 **정지사유**에 들어 있다.

(근거: `20260901_세무사무소목록.xlsx`, 909행 — 2026-09-01 확인)

| 정지사유 | 건수 | 성격 | 필요한 조치 |
|---|---|---|---|
| 장기 미사용으로 인한 서비스 정지 | 121곳 (63%) | 비자발적 | 활용 지원·윈백 |
| 프로모션 종료로 인한 요금제 미설정 | 41곳 (21%) | 비자발적 | 요금제 재선택 안내 |
| 서비스 이용료 2개월 이상 미납 | 25곳 (13%) | 비자발적 | 회수·결제수단 확인 |
| 사유 없음(`-`) | 4곳 (2%) | 사용자 정지로 추정 | 사유 확인 필요 |

- 화면(통합현황 「정지 사유별 현황」)은 **현재 상태='정지'인 곳만** 센다 — 지금 조치가 필요한 대상이라야 뜻이 있다.
- 분류는 사유 문구의 **키워드**로 묶는다(`미납` / `프로모션`·`요금제 미설정` / `미사용`).
  문구가 바뀌면 「기타」로 빠질 뿐 숫자가 사라지지 않는다.

### 「정지」는 화면마다 세는 대상이 다르다 — 확인 필요

## 6. 보류 중인 논의

- **주간회의 ③ 주간 업무 현황의 기준** — 현재 실행기록(LOG) 기반. 직원들이 실제로는 액션 아이템을 주로 쓰므로 전환을 검토했으나, 액션 아이템에 체크 시각(`doneAt`)이 없어 "이번 주에 한 것"을 가려낼 수 없음. **현행 유지로 결정.** 전환하려면 `tgAct`에 체크 시각 저장 추가 필요.
- **가로 탭바 정리** — 사이드바에서는 데이터 품질·담당자·팀 성과·해지방어를 제거했으나, 가로 탭바에는 남아 있음. 제거 여부 미확정.
- **브레드크럼 동기화** — 상단 "사업센터 / OO" 표시가 보드 쪽 내비게이션 기준이라, 대시보드 쪽 탭을 이동해도 따라오지 않음. 수정 가능하나 미착수.
- **긴급도** — 신청 관리 카드의 긴급도 표시는 제거함(요청). 판정 함수(`urg`)는 숨은 필터·전월 대비 집계에서 아직 쓰여 코드에는 남아 있으나 화면에는 노출되지 않는다.
