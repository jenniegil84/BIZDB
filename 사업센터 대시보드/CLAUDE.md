6. 같은 유형을 고칠 때 파일 전체에서 그 패턴을 찾는다.
7. **코드/대시보드 파일을 수정하기 전에, 그 파일이 현재 최신본인지부터 확인한다** — 관련 SKILL.md·프로젝트 지침에 "원본/최신 파일" 언급이 있는지 먼저 확인하고, 파일 안의 버전 번호가 최근 대화·사용자 언급과 맞는지 대조한다. 불일치하면 작업을 진행하기 전에 사용자에게 먼저 확인한다.
8. **수정이 필요한 곳만 찾아서 최소 범위로 읽는다** — grep으로 정확한 줄 위치·호출 경로(예: goTab/RENDER 연결)를 먼저 특정한 뒤, 그 위치에 딱 필요한 범위만 연다. "구조 파악"을 이유로 관련 있을 만한 곳까지 미리 넓게 읽지 않는다. 같은 화면 이름이 서로 다른 렌더링 시스템에 중복 구현된 경우에도, 먼저 좁은 범위에서 실제 호출 경로를 grep으로 확정한 뒤 그 경로만 연다.
9. **"업로드 안 하면 이 값이 화면에 뜬다"는 주장은 소스 코드만 보고 하지 않는다** — 그 값을 만드는 함수(`stdCards()` 등)가 상위에서 통째로 비활성화(`return ''` 같은 이른 반환)돼 있거나, 그 출력을 담는 클래스가 CSS로 전역 숨김(`display:none`) 처리돼 있을 수 있다(9번 섹션 25번 항목). 실제로 화면에 보이는지 Playwright로 확인한 뒤에만 "하드코딩값이 노출된다"고 보고한다.

## 9. 실수 기록 (Claude 실수 발생 시 여기에 추가)

새 실수가 생기면 아래에 번호를 이어서 추가한다. 형식: 무슨 일이 있었는지(증상) → 원인 →
**이후로 지킬 것**. 표가 아니라 이 서술형으로 적는다 — 다음에 이 코드를 만지는 Claude가
같은 실수를 반복하지 않는 게 목적이라, 재발 방지 규칙만 짧게 있는 표보다 증상·원인까지
같이 있는 편이 실제로 도움이 된다.

### 1. "고쳤다"고 말하기 전에 실제 실행 경로를 확인할 것 (2026-08-29)

이 파일(index.html)에는 **같은 화면·같은 기능이 여러 벌 중복 구현**돼 있는 경우가 많다.
(예: 도입문의 화면이 PAY.inq 기반 활성 버전과 INQDATA 기반 레거시 버전 2벌,
"가입채널별 실적" 표가 3곳, "통합 현황" 관련 계산이 board 쪽·dashboard 쪽 따로,
주간회의 화면이 `#content`/`route()`의 `weekShell`·`paintWeek`(`WKKPI_PERF` 기반 —
실제 사이드바 `goTab('week')`가 쓰는 화면)와 `#ixHost` 내부 탭바의 동명 'week' 탭
(`rp-kpi` 리포트 — `ixMount`가 프로그램적으로만 클릭하는, 화면에는 안 보이는 별개
구현) 2벌, "실적 분석 — 누적" 화면이 `#s-cumul`에 그리는 옛 구현("1-D. 실적 분석 —
누적", v05.00 개편 기획안 3-4·5-3 — `RENDER['cumul']`을 먼저 등록하고 자기 자신을
`render()`로 한 번 그리기까지 함)과, 실적 관리 모듈이 나중에 같은 자리에 다시 등록한
`renderCumul`(실제로 화면에 보이는 것) 2벌 — v08.204에서 발견해 옛 구현을 삭제)

소스 코드를 읽고 "여기를 고치면 된다"고 판단한 뒤에도, 실제로:
- 그 함수가 `RENDER['id']`/`goTab`/`gotoTab` 등 실제 호출 경로에 물려 있는지
- 계산식이 매번 다시 실행되는 함수 안에 있는지, 아니면 최초 1회만 실행되는
  바깥 스코프(IIFE 최상단)에 있어서 이후 재렌더에도 절대 안 바뀌는 상태인지

**반드시 jsdom 등으로 직접 실행해서 값이 실제로 바뀌는지 검증한 뒤에만** "고쳤다"고
보고한다. 소스에 수정 사항이 보인다고 해서 그게 실행되는 코드라고 가정하지 않는다.

실제로 이 문제 때문에 같은 버그("가입 vs 해지 추이" 차트가 옛날 값에 고정)를
두 번 잘못 진단하고 두 번째에도 근본 원인(계산이 render() 함수 밖에 있어 재렌더돼도
재계산 안 됨)을 놓칠 뻔했다.

### 2. 버전 번호(title/header 배지)는 매 수정마다 실제로 갱신할 것

코드 주석에는 v08.01~v08.17까지 성실히 기록했지만, 정작 화면에 보이는 버전 배지는
v08.00에서 한참 갱신을 안 했다. 사용자가 "최종 버전 몇이야"라고 물어본 뒤에야 발견됨.
→ 파일을 출력할 때마다 `<title>`, 헤더 배지, hdrBase 세 곳의 버전 문자열을
   그 시점 최신 버전으로 함께 갱신했는지 체크리스트로 확인한다.

**추가 사례 (2026-09-02)** — 사용자 지시로 index.html **화면에는** 버전을 아예 표시하지
않기로 바뀌었다(`<title>`·hdrBase·헤더 배지 모두 제거). 이 예외가 생긴 뒤에도 코드
주석의 버전 이력(`v0X.XX 요청("...")`)은 계속 남긴다 — 화면 노출 여부만 다르고, 다음에
이 코드를 읽는 사람(다음 세션의 Claude 포함)에게는 주석이 유일한 버전 단서가 된다.

### 3. "여러 명이 동시에 쓰는 화면"이라는 전제를 빼먹고 자동 저장을 넣지 말 것 (2026-09-01)

v08.100에서 카드 id 중복(선택 표시 버그) 자동복구를 만들면서, 페이지를 열 때마다(로그인·
세션갱신 포함) **조용히 CARDS·DOCS·ISSUES·LOG·UNIS 전체를 서버에 덮어쓰는 저장**을
같이 넣었다. 이 화면은 엠버·헤나·케이 등 여러 명이 동시에 켜놓고 쓰는 화면이라는 걸
고려하지 않은 채, "중복만 없애면 안전하다"고만 생각했다.

결과: 한 사람이 카드를 만들거나 실행기록을 적는 사이 다른 사람이 페이지만 새로고침해도,
그 자동복구 저장이 "자기가 불러온(그새 낡아버렸을 수 있는) 스냅샷"을 통째로 다시 써서
방금 있었던 편집을 덮어썼다. 실제로 "영업 '구 요금제 전환 영업' 카드 실행기록이
통째로 사라짐" 사고로 이어짐.

**이후로 지킬 것**
- **이 화면처럼 여러 사람이 동시에 접속하는 걸 전제로 하는 곳에서는, "배열/객체 전체를
  통째로 덮어쓰는 저장"을 새로 추가하지 않는다.** 특히 사용자 조작 없이(로드 시점 등)
  자동으로 저장이 나가는 경로는 더 위험하다 — 조작에 걸린 저장은 그나마 그 사람이 뭘
  했는지 알지만, 자동 저장은 "그 순간 이 브라우저가 우연히 들고 있던 스냅샷"을 아무
  맥락 없이 밀어붙인다.
- CARDS·UNIS·DOCS·ISSUES·LOG 다섯 종류는 v08.106에서 3자 병합 저장(base·local·theirs
  비교, MERGEABLE_KINDS·mergeSet·mergeCardMap 참고)으로 바꿨다. **이 다섯 종류를 건드리는
  새 기능을 만들 때는, `m.get()`으로 값을 읽고 병합을 거쳐 저장하는 이 경로를 그대로
  타는지 확인**하고, 별도로 saveToSheet를 우회해 직접 upsert하지 않는다.
- 그 외 나머지 종류(board_keytask·board_budget·board_sem·board_week·board_gorder·
  board_actlog·user_dir·dept_list·board_lastmo)는 **아직 병합 저장이 아니다** — 이
  종류들을 로드 시점에 자동으로 다시 저장하는 코드를 넣기 전에는 반드시 먼저 사용자에게
  "이것도 동시편집 위험이 있다"고 확인받는다.

### 4. CSS 주석 안에 별표+슬래시 조합을 쓰지 말 것 — 주석이 끊겨 바로 아래 규칙이 통째로 죽는다 (2026-09-01)

v08.102에서 CSS 주석에 지운 클래스 목록을 적으면서 `.ww-per` 뒤에 와일드카드 표시(별표)를
붙였는데, 그 별표와 이어진 슬래시가 **주석 종료로 해석**됐다. 그래서 남은 주석 텍스트가
바로 아래 `.ww-cols` 셀렉터 앞에 들러붙었고, 셀렉터 전체가 무효가 되어 **2열 배치 규칙이
브라우저에서 아예 적용되지 않았다.**

증상: 사용자가 "이번주/다음주를 2열로" 요청 → 미디어쿼리를 지우고 "고쳤다"고 보고했으나
화면은 그대로. 두 번 더 엉뚱한 곳(다른 렌더러, 배포 누락, 캐시)을 의심하며 사용자를
세 번이나 헛되이 확인시켰다.

**이후로 지킬 것**
- CSS를 고치고 "됐다"고 말하기 전에, **실제 CSS 파서로 그 규칙이 살아있는지 확인**한다.
  소스에 규칙이 보이는 것과 브라우저가 그 규칙을 받아들이는 것은 다르다.
  ```js
  // jsdom + cssom 으로 검증 — selectorText가 의도한 그대로인지 본다
  const dom = new JSDOM('<style>'+css+'</style>');
  for (const r of dom.window.document.styleSheets[0].cssRules)
    if (r.selectorText === '.타깃') console.log(r.selectorText, r.style.cssText);
  ```
  셀렉터에 주석 찌꺼기가 붙어 있으면 그 규칙은 죽은 것이다.
- 주석에 클래스 목록을 적을 때는 별표·슬래시를 쓰지 말고 쉼표로 나열한다
  (`ww-hd, ww-ttl, ww-per 계열, ...`).

### 5. 데이터 병합·마이그레이션 코드는 "기존 데이터 형태"로 반드시 먼저 테스트할 것 (2026-09-01)

v08.106에서 동시편집 유실을 막으려 병합 저장을 넣으면서, 항목 짝짓기를 `x.id`로만 했다.
그런데 **예전에 저장된 실행기록·문서·논의사항에는 id가 아예 없었다.** 불러오는 쪽에서만
임의 id를 붙이고(backfillEntryIds) 서버 원본은 그대로 뒀더니, 병합 시 서버 쪽 항목이
전부 「id 없음」 하나로 뭉개졌고 짝을 못 찾은 기존 기록은 「상대가 지웠다」로 판정돼
삭제됐다. **결과: 8월 실행기록이 카드당 1건만 남고 사라짐.** 유실을 막으려고 넣은 코드가
오히려 더 큰 유실을 냈다.

내가 v08.106에서 돌린 테스트는 전부 **id가 있는 새 데이터**로만 만들었다. 실제 서버에
쌓여 있는 **id 없는 옛 데이터**로는 한 번도 돌려보지 않았다.

**이후로 지킬 것**
- 저장 형식을 바꾸거나 병합·마이그레이션 코드를 넣을 때는, **반드시 "기존에 저장돼 있던
  형태"의 데이터로 먼저 테스트**한다. 새 형식으로만 테스트하면 마이그레이션 경로가
  통째로 검증되지 않는다.
- 특히 **"짝을 못 찾음 → 삭제"로 이어지는 로직**은 위험하다. 짝짓기 키가 양쪽 데이터에
  모두 존재하는지 먼저 확인하고, 확신이 없으면 **삭제 대신 합치기(union)** 로 기울인다.
  v08.110에서 기준 스냅샷이 없는 카드는 삭제 판정을 아예 하지 않도록 안전장치를 넣었다.

### 6. 카드·표 안에 설명 문장을 넣지 말 것 — 라벨·값·증감만 (2026-09-01)

이 화면은 v06.96에서 이미 정해 뒀다: **「카드 안 설명 제거 — 라벨·값·증감만 남긴다.
산출 기준은 코드 주석과 버전 이력에 남기고 화면에는 결과만 둔다.」** v06.88에서는
「자동」 배지와 산출 기준 툴팁도 같은 이유로 뺐다.

그런데 v08.124에서 「유입경로 확인 8건 · 미확인 5건 (목록 「미분류」 5건)」을,
v08.129에서 KPI 칸마다 「요금제만 하향 · 고객 유지」 같은 기준 줄과 툴팁을 다시 넣었다.
둘 다 "친절하게 설명하면 좋겠지"라는 생각이었지만, 사용자가 이미 "정신없다"고 두 번
말한 화면에 글자를 더 넣은 것이다. 결국 "이런 세부설명은 다 빼라고 했잖아"라는 지적을 받았다.

**이후로 지킬 것**
- 카드·KPI 칸·표 행에 **설명 문장(무엇을 어떻게 세는지)을 넣지 않는다.** 툴팁도 마찬가지다.
  넣어도 되는 것은 **라벨 · 값 · 증감 · 그 값을 이루는 항목 목록**뿐이다.
- 숫자의 근거를 보여줘야 한다면 **문장이 아니라 목록의 한 줄로** 넣는다. 예: 유입경로
  미확인을 문장으로 적는 대신 목록에 「미분류 5건」 줄을 두면, 설명 없이도 목록 합계가
  총건과 맞아 화면에서 바로 검산된다(v08.130).
- 산출 기준은 **코드 주석에만** 남긴다. 사용자는 코드를 안 보지만, 다음에 이 코드를 읽는
  사람에게는 그게 제자리다.
- **화면을 정리해 달라는 요청을 받은 뒤에는 특히**, 새 기능을 넣을 때 글자가 늘지 않는지
  먼저 확인한다. 요청은 "덜어내라"인데 반대로 가고 있지 않은지 본다.

**세 번째 위반 (v08.171 · 2026-09-01)** — 채널 미지정 건을 표에서 뺀 뒤
「채널 미지정 18건은 제외했습니다 — 실적 관리에서 지정하면 여기에 반영됩니다」를 표 밖에 붙였다.
이번에는 **레이아웃까지 깨졌다** — 3열 그리드에 칸이 하나 더 생겨 표가 줄바꿈됐다.
사용자는 "안내문구 표시하지 말라고 했잖아"라고 다시 지적했다.

- **"이건 설명이 아니라 안내다"라고 스스로 예외를 만들지 않는다.** 값과 숫자가 아니면 넣지 않는다.
- 알려야 할 것이 있으면 **제목이나 숫자에 녹인다.** 여기서는 제목의 「(실적 기준)」과
  요약 줄의 건수만으로 충분했다.
- **그리드 안에 요소를 더하면 칸 수가 바뀐다.** 표 옆에 무언가를 붙이기 전에 그 부모가
  `grid-template-columns`로 칸 수를 고정하고 있는지 확인한다.

### 7. 모든 보고 내용은 두괄식 — 결론 먼저, 근거 뒤 (2026-09-01)

화면이든 문서든 채팅 회신이든 **결론을 앞에 두고 근거를 뒤에 둔다.**
정책 문서 `사업센터_정책정리_v01_17.md` 「두괄식 — 모든 보고 내용의 기본 형식」에 확정.

- **채팅 회신**: 무엇을 했는지·무엇이 원인인지를 첫 줄에 쓴다. 조사 과정·시도한 것들을
  앞에 늘어놓지 않는다. 순서는 **결론 → 근거 → 확인 필요**.
- **화면**: 핵심 지표를 큰 카드로 위에, 나머지는 「세부 지표」로 아래에. 표는 위에 결론 한 줄,
  목록은 상위 몇 건 + 더보기.
- **버그를 고쳤을 때**: "원인은 X였습니다"를 먼저 쓴다. 어디를 어떻게 뒤졌는지는 필요할 때만
  뒤에 짧게 붙인다.

### 8. 저장할 때 "빈 것"을 지우지 말 것 — 키가 없어지면 화면이 조용히 깨진다 (2026-09-01)

v08.111 병합 저장에서 `if(arr.length)out[cid]=arr;` 로, **항목이 0건인 카드는 키를 아예
만들지 않았다.** 용량을 아끼려는 생각이었다. 그 값이 서버에 저장되고 다시 불러오면 LOG가
통째로 교체되면서 그 카드의 키가 사라지고, `LOG[id].push(...)`가 undefined에 push하는 셈이
되어 예외가 났다. 화면에는 아무 일도 일어나지 않아 **「입력했는데 저장이 안 된다」**로 보였다.

**이후로 지킬 것**
- 저장할 값에서 **빈 배열·빈 객체를 제거하지 않는다.** 아끼는 용량은 미미하고, 키가 사라지면
  그 키를 당연히 있다고 보고 쓰는 코드가 전부 깨진다.
- 컬렉션에 접근하는 코드는 **항상 없을 수 있다고 보고 쓴다** — 넣을 때는
  `(X[id]=X[id]||[]).push(...)`, 지우거나 고칠 때는 `if(!X[id])return;`.
- 이 실수는 5번(기존 데이터 형태로 테스트)의 다른 얼굴이다. **저장 형식을 바꾸면 그 값을
  다시 읽어 쓰는 화면까지 한 번은 돌려본다** — 저장이 성공하는 것과 그 값으로 화면이
  동작하는 것은 다른 문제다.

### 9. 기존 클래스를 쓰기 전에 그 클래스가 화면에 보이는지 확인할 것 (2026-09-01)

「데이터 없음」 안내를 `.notebox`로 넣었는데 화면에 아무것도 나오지 않았다. 원인은
v03.67에서 **`#ixHost .notebox:not(.summary){display:none !important;}`** 로 안내문을
전면 숨겨 둔 것이었다. 그 규칙을 모른 채 그 클래스를 재사용했고, 마크업은 정상적으로
만들어졌지만 브라우저가 그리지 않았다. 코드만 보면 멀쩡해 보여 원인을 찾기 어려웠다.

**이후로 지킬 것**
- 기존 클래스를 재사용할 때는 **그 클래스에 걸린 규칙을 먼저 훑는다.**
  특히 `display:none`·`!important`·`:not(...)` 같은 전역 숨김 규칙이 있는지 본다.
  ```bash
  grep -n "\.클래스명" index.html | grep -i "display\|important"
  ```
- 새 요소를 넣었는데 화면에 안 보이면, **마크업이 만들어졌는지가 아니라 계산된 display를**
  확인한다. jsdom으로 `getComputedStyle(el).display`를 찍어 보면 바로 드러난다.
- 숨김 규칙을 발견해도 **그 규칙을 풀지 않는다** — 다른 화면에서 일부러 숨긴 것이 되살아난다.
  내가 넣는 쪽에서 다른 방법(여기서는 카드 한 장)을 쓴다.

### 10. 입력 중인 칸을 다시 그리지 말 것 — 치던 글자가 날아간다 (2026-09-01)

「기간에 12월 31일을 넣으면 3만 들어간다」는 신고. 원인은 `onchange` 핸들러가 값을 저장한 뒤
`paintPage()`로 상세 패널을 통째로 다시 그린 것이었다. 날짜 칸(type=date)은 연·월·일이
나뉘어 있어 「3」을 친 순간에도 값이 유효해져 change가 한 번 나는데, 그때 입력 칸이 새로
만들어지면서 뒤이어 친 「1」이 갈 곳을 잃었다. 실행기록·문서·논의의 글자 입력도 같았다.

**이후로 지킬 것**
- **입력 칸의 change/input 핸들러에서 그 칸이 들어 있는 영역을 다시 그리지 않는다.**
  값은 이미 화면에 들어가 있으므로 다시 그릴 이유가 없다.
- 같이 바뀌어야 하는 표시(여기서는 「총 N일」)가 있으면 **그 자리만 id로 찾아 직접 고친다.**
- 다시 그려야만 하는 변경(상태·담당자처럼 목록 위치가 바뀌는 것)은 예외로 두되,
  **어떤 필드가 그런지 명시**한다. 전부 다시 그리는 편이 편해 보이지만 입력을 망가뜨린다.

**두 번째 사례 (v08.189 · 2026-09-02)** — 실적 관리 기간 칸에 「2026」을 치면 연도 한 자마다
(2 → 20 → 202) 값이 유효해져 change가 나고, 그때마다 목록을 다시 그려 **`0002-08-01`** 이
들어갔다. v08.164에서 카드 상세만 고치고 **다른 화면의 날짜 칸은 같이 보지 않은 것이 원인이다.**

- **같은 유형의 버그를 고칠 때는 그 패턴을 파일 전체에서 찾는다.**
  `grep -n 'type="date"'` 한 번이면 어느 화면이 남았는지 바로 보인다.
  이번에도 그렇게 해서 일별 탭(`daySet`)도 같은 문제인 것을 함께 찾았다.
- 날짜 칸은 **연도가 4자리가 되기 전에는 다시 그리지 않고**, 완성 뒤에도 잠깐(400ms) 기다렸다
  그린다. 이어 치면 타이머가 다시 잡힌다. **값 저장은 매번 한다** — 저장이 늦으면 안 된다.

### 11. `node --check`는 선언 순서 오류를 못 잡는다 — 페이지를 실제로 실행해 볼 것 (2026-09-02)

「데이터가 없어졌어」 신고. 원인은 v08.180에서 `plusAll`을 `plusConv`보다 **위에** 둔 것이었다.
`const`는 선언 전에 쓰면 그 자리에서 `ReferenceError: Cannot access 'plusConv' before
initialization`이 난다. 그 오류로 `perfStat`이 매번 터졌고, 화면은 코드에 박힌 옛 기본값
(903곳·2026-08-26)으로 굳었다. **파일을 새로 올려도 숫자가 안 바뀌던 이유다.**

문법 검사(`node --check`)는 이걸 통과시킨다 — 문법은 맞고 실행 시점에만 터지기 때문이다.
매 버전 문법 검사만 하고 넘어가서 네 버전(v08.180~183) 동안 깨진 채로 배포됐다.

**이후로 지킬 것**
- **함수 하나를 고쳤으면 그 함수를 실제로 한 번 호출해 본다.** 지금까지 추출해서 단위 테스트한
  것은 잘 했지만, 추출 과정에서 선언 순서가 재배치돼 원본의 순서 문제가 가려졌다.
- **배포 전에 페이지 전체를 jsdom으로 띄워 오류를 확인한다.** 아래 한 번이면 잡힌다:
  ```bash
  # runScripts:'dangerously'로 로드 → virtualConsole로 jsdomError·error 수집
  # /getContext|scale/ 같은 캔버스 잡음만 걸러내고 나머지가 있으면 배포 중단
  ```
- **화면이 「옛날 값」을 보여주면 데이터 문제가 아니라 코드가 죽은 것부터 의심한다.**
  이번에도 파일·컬럼·용량·저장 경로를 다 확인한 뒤에야 실행 오류를 찾았다.
  순서를 뒤집었어야 했다 — **먼저 콘솔 오류, 그다음 데이터.**
- **하드코딩된 기본값(`window.__xlOffice = ... || {큰 스냅샷}`)이 이 사고를 키웠다.**
  데이터가 없을 때 「데이터 없음」이 아니라 그럴듯한 옛 숫자를 보여줘 원인 파악을 늦췄다.
  (해결) v08.204에서 이 스냅샷을 걷어내고 `null`로 바꿨다 — 자세한 내용은 17번 참고.

### 12. 집계의 「기준」이 되는 값도 저장·복원 대상인지 확인할 것 (2026-09-02)

11번을 고친 뒤에도 화면이 903곳으로 남았다. 원인은 **기준일(`__baseDate`)이 저장 대상이 아니어서**
새로고침하면 기본값 `2026-08-26`으로 돌아간 것이었다. 데이터는 909행 그대로였지만 화면은
그 날짜까지만 세어 903곳(909 − 그 뒤 가입 6건)이 됐다. 해지 319(=321−2)·정지 188(=191−3)도
같은 이유였다.

**데이터가 맞는데 숫자가 조금씩 작다면 데이터가 아니라 기간을 의심한다.**
`909 − 903 = 6`처럼 차이가 작고 일정하면 잘림(cutoff)이지 소실이 아니다.

**이후로 지킬 것**
- 새 상태값을 만들 때 **저장·복원 맵(`MERGEABLE_KINDS`·`SHEET` 표)에 넣을지 반드시 판단**한다.
  안 넣기로 했다면 **로드 시 무엇으로부터 다시 계산할지**를 함께 정한다.
  (여기서는 업로드 자료의 최신 날짜로 다시 맞추도록 했다 — v08.185)
- 기간·기준월처럼 **모든 집계에 곱해지는 값**은 틀리면 화면 전체가 조용히 어긋난다.
  값 하나가 아니라 화면 전체가 이상할 때 이런 「기준값」부터 본다.

### 13. 고치기 전에 「화면이 실제로 부르는 함수」를 확인할 것 (2026-09-02)

「8월 요금제 변경이 실적 관리에 빠져 있다」는 신고를 받고 v08.190에서 `pmMasterGap()`을 고쳤다.
그런데 화면이 부르는 함수는 **`pmOrphanRows()`** 였다. 이름이 다른 두 함수가 같은 일을 하고 있었고,
내가 고친 쪽은 아무 데서도 쓰이지 않았다. 사용자는 배포 후에도 「2건」 그대로를 봤다.

**이후로 지킬 것**
- 함수를 고치기 전에 **그 함수가 어디서 호출되는지 먼저 센다.** `grep -n '함수명' index.html`에서
  정의 한 줄만 나오면 그건 죽은 코드다.
- **같은 일을 하는 함수가 둘 있으면 그 자체가 결함이다.** 하나로 합치거나, 합칠 수 없으면
  둘 다 고치고 주석에 서로를 가리킨다. 이번엔 `pmMasterGap`이 v08.167에서 만들었다가
  화면 연결만 다른 함수로 간 흔적이었다.
- **재현 테스트는 화면이 쓰는 경로로 한다.** 추출해서 단위 테스트하면 죽은 함수도 잘 통과한다.
  페이지를 띄워 `window.pmOrphanRows()`처럼 실제 함수를 불러 확인했어야 했다.

**두 번째 사례 (v08.192 → v08.193 · 2026-09-02)** — 신청 관리의 「해지신청」 탭을
「고객 현황」으로 바꿨는데 **탭 이름만 바뀌고 내용은 해지신청 표 그대로**였다.
옛 렌더를 부르는 곳이 **세 군데**였고(셸 · 탭 전환 핸들러 · `RENDER` 등록) 나는 셸 하나만 고쳤다.

- **한 화면을 그리는 경로가 여럿일 수 있다.** 컨테이너 id로 grep해 **그 안을 채우는 코드를 전부**
  찾는다. `grep -n 'churnReqPaneWrap'` 한 번이면 다섯 군데가 나왔다.
- 검증도 **탭을 눌러 보고, 화면을 떠났다 돌아와 본다.** 함수 하나만 불러 확인하면 다른 경로가 남는다.

같은 수정에서 **두 화면의 기준이 어긋난 것도 발견했다** — 이 목록은 제외 규칙(변경 전=후,
구간요금제→베이직)을 적용하지 않아 27건, 실적 분석은 22건이었다.
**같은 데이터를 세는 화면이 둘이면 기준도 한 곳에서 와야 한다.**

### 14. 카드와 그 상세는 같은 목록에서 세울 것 (2026-09-02)

「카드상세와 맞지않음」 신고. 실적 관리의 카드 4종은 **필터 적용 결과**(28건)를 세는데,
카드를 눌러 열리는 상세는 **필터 이전 전체**(1,787건)를 봤다. 같은 이름의 값이 두 숫자를 냈다.

원인은 두 곳이 서로 다른 함수를 쓴 것이다 — 카드는 `pmRows()`(필터 적용), 상세는 `pmSrcRows()`(원본).

**이후로 지킬 것**
- **숫자를 보여주는 곳과 그 숫자를 펼쳐 보는 곳은 같은 함수를 쓴다.** 조건을 두 번 쓰면
  한쪽만 고쳐져 어긋난다. 이번엔 상세가 `pmRows()`를 쓰도록 바꿔 구조적으로 같아지게 했다.
- **일부러 다른 모수를 쓰는 경우**(여기서는 「명단 대조」 — 명단 34곳 전체와 맞춰야 하므로
  기간을 걸면 뜻이 달라진다)는 **그 사실을 화면에 밝힌다.** 안 밝히면 이것도 버그로 읽힌다.
- 검증은 **필터 조건을 바꿔 가며** 한다. 한 조건에서만 맞으면 못 잡는다
  (이번엔 8월·전체·7월·검색 네 상황 × 카드 4종 = 16개 조합을 확인했다).

### 15. 파일이 지금 최신본인지 확인하지 않고 고치면 헛수고가 된다 (2026-09-02)

Claude 프로젝트 문서에 저장된 index.html(내부 표기 v05.20)을 최신본으로 오인하고 그 위에

  SKILL.md·프로젝트 지침에 "원본/최신 파일" 언급이 있는지 먼저 보고, 파일 안 버전
  번호가 최근 대화·사용자 언급과 맞는지 대조한다.

### 18. 메뉴에서 뺀 화면이 코드에는 그대로 남아있던 것을 확인 후 완전 삭제 (2026-09-02)

`<section id="s-qual">` 같은 빈 컨테이너가 페이지 로드 시 계속 만들어지고 있었다 —
그 컨테이너에 각 화면의 렌더 코드가 `opsPage(document.getElementById('s-def'),...)`처럼

**보여주는 방법 관련 시행착오** — Playwright로 화면 내용을 직접 캡처하려 했으나,

버튼)가 화면을 가려 스크린샷이 계속 실패했다. **화면을 강제로 띄워 스크린샷 찍는 대신,

결과를 그대로 확인할 수 있다는 걸 기억해 둔다. 이 시행착오로 사용자에게 "왜 이렇게

우회, `.on`/`.active` 클래스 강제 등)은 스크린샷이 꼭 필요할 때만 시도하고, 텍스트

- 값을 "제거해달라"는 요청을 받으면, 지우기 전에 **그 값이 화면에 실제로 렌더되는지부터
  확인**한다(8-2번 규칙). 렌더되지 않는 죽은 값이면 대체 계산식을 고민할 필요 없이 그냥
  지우면 되고, 렌더되는 값이면 `null`/`'—'` 같은 안전한 빈 상태로 바꾸되 근거 없는 새
  산식은 만들지 않는다.

### 20. grep의 `\b`(단어 경계)는 한글 앞뒤에서 믿을 수 없다 — "죽은 필드"를 잘못 골라 실사용 데이터를 지웠다 (2026-09-02)

"PAY 객체 정리계획 실행해" 요청을 받아, 이전 세션에서 이미 "0회 사용"으로 분류해 둔 `PAY.agg`
필드 24개를 grep으로 재확인한 뒤 삭제했다. 재확인에 쓴 정규식이 `\.${키}\b` 형태였는데, **`\b`는
직전 문자가 "단어 문자(`\w`)"일 때만 경계로 인식한다 — 그런데 grep/정규식 엔진 기본 설정에서
한글은 `\w`가 아니다.** 그래서 `A.일시납스케줄.map(...)`처럼 한글 키 바로 뒤에 마침표가 오는 실제
사용처가 있었는데도, "한글(비단어) 다음에 마침표(비단어)"라 경계가 성립하지 않아 **매치 자체가
안 잡혔다.** 그 결과 `위험`·`일시납확정`·`일시납스케줄` 세 필드가 "0회 사용(죽은 필드)"으로
오판되어 삭제됐고, 그중 `일시납스케줄`은 프로모션 화면 렌더러(`render()`, `#s-promo`)에서
`A.일시납스케줄.map(...)`을 바로 호출해 **화면이 그 자리에서 즉시 깨졌다**(`TypeError: Cannot
read properties of undefined (reading 'map')`). 다행히 "고친 뒤 페이지를 실제로 띄워 오류
확인"(CLAUDE.md 8-3번) 절차를 그대로 따른 덕에 배포 전 Playwright 검증에서 바로 잡혔다.

더 큰 문제는 **원본 값 복구**였다. `위험:123`은 이번 대화 중 다른 목적으로 떠 있던 로그에
우연히 남아 있어 복구했지만, `일시납확정`(금액)과 `일시납스케줄`(사무소별 일시납 종료 스케줄
배열, 사무소명·유형·시작일·종료일 등을 담은 실데이터)은 **삭제 전 백업을 따로 안 만들어서
원본 수치를 복구할 방법이 없었다.** 지어낼 수도 없어(이 자체가 CLAUDE.md 17번이 금지하는
"근거 없는 값 만들기") 두 필드 모두 안전한 빈 값(`A.일시납스케줄||[]`, `A.일시납확정!=null`
가드)으로 처리하고 사용자에게 원본 파일 확인을 요청했다 — **한 번 잘못 지우면 문법 검사·화면
확인으로는 못 잡는 손실(원본 데이터 자체의 소실)이 남는다.**

**이후로 지킬 것**
- **grep으로 "이 필드는 0회 사용(죽은 코드)"이라고 판단할 때, 필드명에 한글이 포함돼 있으면
  `\b`를 쓰지 않는다.** 대신 `[A-Za-z0-9_]\.필드명` + `\['필드명'\]`처럼 앞뒤를 문자 클래스로
  직접 지정하거나, 최소한 두 가지 다른 방식(단어 경계 방식 + 전체 텍스트 카운트 대조)으로
  교차 검증한다. 이번에도 "전체 발생 횟수"만 따로 세어봤다면 `일시납스케줄`이 2회 나온다는
  게 바로 보였을 것이다.
- **"이전에 죽은 코드로 분류해 둔 목록"이라도 실제로 지우기 직전에는 다시 grep한다** — 이번
  분류 자체는 이전 세션 결과를 재사용한 것이었는데, 도구(정규식)가 문제였으므로 몇 번을
  재확인해도 같은 실수가 반복될 뻔했다. 정규식 자체의 신뢰성(한글 `\b` 문제)을 의심하는 게
  먼저였다.
- **대량 필드를 한 번에 삭제하는 작업(JSON 파싱 후 여러 키 제거)을 하기 전에는, 삭제 전
  원본 줄을 별도 변수/파일에 남겨 둔다.** 검증에서 걸러지지 않는 실수(문법 오류·pageerror
  없이 그냥 원본 숫자만 사라지는 경우)를 되돌릴 유일한 방법이기 때문이다. 이번엔 문법
  오류로 걸러졌지만, 정지된 데이터베이스 값이 조용히 사라지는 경우엔 이 방법이 아니면 못
  잡는다.

확인했다.

### 23. "UX팀 담당 업무 실적" 카드는 코드에는 있지만 지금 어떤 메뉴로도 열리지 않는 죽은 화면이었다 (2026-09-03)

`innerText`로만 확인하고 "화면에 실제로 보이는지"는 따로 검증하지 않은 채 "UX 탭 카드"라고
적었는데, 이번에 `goTab('ux')`가 실제로 그리는 화면과 대조해보니 **완전히 다른 화면**이었다.

**확인된 구조 (18번·1번 항목과 같은 유형의 중복 구현)**
- 지금 사이드바 "UX" 메뉴(`goTab('ux')`)를 누르면 `route()`가 `TAB==='ux'`일 때
  `shell()`/`paint()`(노션형 칸반 보드 — 카드·표·예산, `CARDS`/`DOCS`/`ISSUES` 등)를
  `#page`에 그린다. **"담당 업무 실적"이라는 문구 자체가 이 화면에 없다.**
- "담당 업무 실적" 카드(도입문의·컨설팅·온보딩·활성화 모니터링·문의상담 5칸, `uxPerf()`
  함수, `RENDER['ux']=render`)는 `#mainroot` 안 `<section id="s-ux">`에 그려지는데, 이
  섹션은 `TABS` 배열(`#ixHost`의 자체 탭바용, 4368행 `{id:'ux',...}`)에는 들어 있지만
  **`IX_TABS`(11177행, 사이드바 이식 어댑터가 실제로 노출하는 탭 목록)에는 없다.**
  `route()`는 `IX_TABS`에 있는 탭만 `ixMount()`로 `#ixHost`를 꺼내 보여주고, `ux`/`mkt`/`biz`는
  처음부터 다른 분기(`shell()`)로 빠지면서 `ixUnmount()`가 `#ixHost`를 숨긴다 — 그 결과
  `#s-ux`는 페이지 로드 시 딱 한 번(`render()` 자체 호출, 6840행) 채워진 뒤 **영원히
  `display:none` 상태로 DOM에만 남는다.** 사용자·팀원 누구도 이 화면을 볼 방법이 없다.
- 출처도 재확인 결과 정정 필요 — 21번은 "`PAY.funnelStat.cust_total`"이라 적었지만, 실제로
  이 카드의 "활성화 모니터링" 칸은 `PF.use=useRiskStat()`을 쓰고, `useRiskStat()`(7971행)은
  `(PAY.monStat||{}).total||0`을 읽는다. 즉 진짜 출처는 **`PAY.monStat.total`**이고, 이 값도
  세무사무소목록 업로드(`xlParseMonitor`)로 덮어써지기 전까지는 PAY 리터럴 스냅샷(392) 그대로다
  — `funnelStat.cust_total`과 우연히 같은 숫자(392)라 혼동했다.

**처리 여부 (2026-09-03 갱신)** — 목업으로 위치를 보여준 뒤, 사용자가 "이 화면, 아예 지울까요
살려서 어딘가에 다시 연결할까요?"라는 질문에 **"아예 지워"**라고 확정해, index.html v08.213에서
완전히 삭제했다. "팀탭 업무카드는 절대 손대지마"(이전 지시)의 대상은 이 죽은 카드가 아니라
실제로 보이는 칸반 카드(`CARDS`)라는 점도 이번에 명확해져, 삭제 범위와 겹치지 않는다.

**삭제 내용 (index.html v08.213)**
- `uxPerf()`·`render()`(`#s-ux` 대상)와 그 부속 UX 업무/프로젝트/문서 CRUD 함수·상태 전체
  (원래 6480~6845행, 366줄짜리 IIFE 하나)를 삭제하고 그 자리에 삭제 사유·범위를 적은 주석으로

- `TABS` 배열의 `{id:'ux',nm:'UX',st:'full'}` 항목(과 그 위 `// ── 팀 업무 ──` 주석)도 함께
  삭제 — 이 항목이 남아 있으면 아무도 못 보는 빈 `<section id="s-ux">`가 페이지 로드마다
  계속 만들어지기 때문이다(18번 항목과 같은 유형).
- `useRiskStat()`(7971행, 삭제 블록 **밖**에 별도로 정의됨)은 다른 곳(11042행)에서 여전히
  쓰여 손대지 않았다 — 죽은 건 그걸 부르던 `uxPerf()` 쪽이지 `useRiskStat()` 자신이 아니다.
- Supabase 저장/복원 키 매핑(`ux_tasks`·`ux_task_monthly`·`ux_projects`·`ux_docs`·
  `ux_monitoring`·`ux_plus_target`·`ux_requests`·`ux_issues`, 4783~4786행 부근)은 **의도적으로
  손대지 않았다** — 이번 요청은 "화면 삭제"이지 "과거 Supabase 데이터 삭제"가 아니고, 매핑을
  지우면 혹시 남아있을 과거 데이터를 되돌릴 방법이 없어지기 때문이다.
- 검증: `new Function()` 문법 검사(6개 스크립트 블록 전부 통과) + Playwright로 NAV 17개 탭
  전부 `goTab()` 이동 후 `pageerror`/콘솔 에러 0건 확인(네트워크 차단 잡음 제외) +
  `document.getElementById('s-ux')`가 `null`이 됐음을 확인 + `goTab('ux')`가 여전히 칸반
  보드(`팀스페이스`·`카드 17`·`예산` 등)를 정상적으로 그리는 것을 `innerText`로 대조 확인.

**이후로 지킬 것**
- **카드·화면 내용을 `innerText`로 확인했다고 해서 "사용자에게 보이는 화면"이라고 단정하지
  않는다.** `getElementById`가 값을 찾았다는 것과 그 요소가 현재 내비게이션 경로로 도달
  가능하다는 것은 다른 문제다(18번 항목과 같은 함정). 의심되면 그 화면으로 실제 이어지는
  메뉴/탭을 `goTab()`으로 눌러 같은 문구가 뜨는지 대조한다.
- 같은 `id`(`ux`)를 쓰는 화면이 `TABS`(레거시 `#ixHost`용)와 `IX_TABS`(사이드바 실제 노출용)
  양쪽에 **다르게** 걸려 있을 수 있다 — 하나에 있다고 다른 하나에도 있다고 가정하지 않는다.

### 24. "프로모션 종료·정상가 전환" 화면 일부가 업로드 없이도 PAY 리터럴 스냅샷을 그대로 보여준다 (2026-09-03)

Claude 실수는 아니고, 사용자가 "고객관리의 프로모션종료·정상가전환, 해지·재가입 탭은 데이터
업로드가 반영된 데이터야?"라고 물어 코드를 대조 확인한 결과다. 코드 수정은 하지 않고 확인만
했다 — 아래는 그 결과.

**해지·재가입 화면 — 전부 업로드 연동 확인됨**
카드(대상·신규·완료)는 `window.__xlOffice`(세무사무소목록 업로드) 값을 직접 읽고, 없으면
`'—'`. 해지 사유 랭킹은 21번 항목에서 이미 고친 대로 `window.__xlOffice` 존재 여부로 게이트.
발생 건 목록(`rows`)은 `churnRowsLive()`(`window.__xlOfficeRows` 기준)가 있으면 그걸 쓰고,
없으면 `A.churn_rows`인데 이 필드는 PAY 리터럴에서도 처음부터 빈 배열(`[]`)이라 안전하다.
**결론: 이 화면은 업로드 전엔 정직하게 비어 있고, 업로드하면 그 값을 그대로 반영한다.**

**프로모션 종료·정상가 전환 화면 — 표는 연동, 상단 KPI 카드 일부는 미연동(확인 필요)**
- **연동됨**: "종료 관리 목록"(`A.promo_rows`)·"프로모션 코드 적용 전체 현황"·업체별 목록은
  전부 `window.__xlBilling`(청구내역파일 업로드)이 있어야만 채워지는 `__syncPromo()`/
  `billRecs()` 경로를 탄다. 업로드 전엔 빈 표/"업로드 필요" 문구가 정상적으로 뜬다.
- **미연동 — 확인 필요**: 상단 `stdCards`의 **"대상"**(`A.종료임박+A.종료경과+11`)과
  **"미처리"**(`A.종료임박+1`)는 `A.종료임박`/`A.종료경과`를 **게이트 없이 직접** 쓴다. 그런데
  이 두 필드는 `window.__xlBilling`이 있을 때만 `__syncPromo()`가 실데이터로 덮어쓰고
  (2936행), 없으면 리셋(`__resetUploadData`, 2872행)을 누르지 않는 한 **PAY 리터럴 스냅샷
  값(종료임박 26·종료경과 49)이 그대로 남는다.** 즉 **청구내역파일을 한 번도 안 올려도
  "대상 86곳"·"미처리 27곳"이 뜬다** — 21번 항목에서 이미 고친 것과 같은 유형의 문제가
  이 두 칸에는 아직 남아 있다.
- **처음부터 항상 정적(업로드와 무관)인 것들** — 버그는 아니고 애초에 데이터 연동 자체가
  없는 자리들:
  - "기한초과" 카드(`'셈 1(검증 필요)'`)·손실 카드(`'전환 실패 시 −70만/월~'`) — 특정
    사무소("셈") 조사 결과·가정치를 텍스트로 박아 둔 것. 업로드해도 안 바뀐다.
  - "190만 일시납 — 종료 안내 스케줄" 표(`A.일시납스케줄`) — 20번 항목에서 원본 수치를

    없어 **항상 빈 표**다.
  - 하단 인사이트 9항목(`ninePanel`)의 구체적 숫자들(경과 49곳·정지사유 2위 129건·
    3개월 내 26곳·전환 성공 시 +70만/+875만 등) — 전부 과거 특정 시점 조사 결과를 텍스트로
    적어 둔 것이라, 업로드해도 함께 바뀌지 않는다.

**이후로 지킬 것**
- "이 화면 실데이터 맞아?"류 질문을 받으면 화면 전체를 하나로 답하지 않는다 — **표/카드
  단위로 어느 필드를 쓰는지, 그 필드가 게이트(업로드 존재 확인) 없이 리터럴 기본값을
  직접 참조하는지**를 하나씩 grep으로 대조해야 21번 항목 같은 "일부만 실데이터" 케이스를
  놓치지 않는다.
- 위 "대상"·"미처리" 카드는 **사용자 확인 후 처리** — 이번엔 질문에 답만 하고 코드는
  손대지 않았다(요청받지 않은 수정 금지 원칙). 고치기로 하면 21번 항목과 같은 패턴
  (`window.__xlBilling` 존재 여부로 게이트, 없으면 `'—'`)을 그대로 적용하면 된다.

**정정 (2026-09-03, 25번 항목 참고)** — 위 "대상"·"미처리" 카드가 "업로드 안 해도 86곳·27곳이
뜬다"는 부분은 **소스 코드만 보고 판단해 틀렸다.** 실제로는 `stdCards()` 자체가
`return '';`(4670행, v03.76부터 전 탭에서 비활성화)로 시작해 이 카드 자체가 어느 화면에서도
전혀 렌더링되지 않는다 — 안 보이니 하드코딩값도 노출될 수 없었다. Playwright로 직접 확인하지
않고 소스만 보고 "노출된다"고 보고한 것 자체가 실수다(25번 항목에 기록). 다만 이후 사용자가
"모든 데이터값은 하드코딩하지 않는다"고 정책을 확정해, 언젠가 `stdCards()`가 재활성화될
경우를 대비해 게이트는 그대로 적용해 뒀다(index.html v08.214) — 지금 당장 화면이 바뀌는
효과는 없다.

### 25. "소스에 하드코딩값이 있다" = "화면에 노출된다"가 아니다 — Playwright로 확인 안 하고 보고한 실수 (2026-09-03)

사용자가 "프로모션·해지재가입 탭이 업로드 반영되냐"고 물어 24번 항목을 쓸 때, 프로모션
화면 상단 `stdCards`의 "대상"(`A.종료임박+A.종료경과+11`)·"미처리"(`A.종료임박+1`)가
청구내역파일 미업로드 시 PAY 리터럴 스냅샷(26·49)을 그대로 노출한다고 **소스 코드 읽기만으로**
보고했다. 그런데 사용자가 이어서 "데이터값은 없으면 없는대로, 하드코딩 금지"라고 정책을
확정해 실제로 고치려고 Playwright로 화면을 띄워보니, `stdCards()` 함수 자체가

```js
function stdCards(o,clicks,defs){
  return ''; // v03.76 실적 카드 전 탭 제거 (요청) — 복원: 이 줄 삭제
  ... // 아래는 전부 도달 불가능한 죽은 코드
}
```

로 **v03.76부터 전 탭에서 통째로 비활성화**돼 있었다 — 첫 줄에서 빈 문자열을 반환하고
끝나, 인자로 뭘 넘기든 그 뒤 로직(대상·미처리 계산 포함)은 한 번도 실행되지 않는다.
즉 **이 카드는 프로모션 화면뿐 아니라 `opsPage()`를 쓰는 해지·재가입 등 다른 화면에서도
전혀 렌더링되지 않는다.** 안 보이는 값이니 하드코딩이든 실데이터든 노출될 방법이 없었다 —
"소스에 하드코딩값이 보인다"와 "그 값이 사용자 화면에 뜬다"를 같은 것으로 취급한 게 원인이다.

같은 이유로 프로모션 화면 하단 "인사이트 9항목"(`ninePanel()`)도 확인해보니, 함수 자체는
정상 실행되지만 그 출력을 담는 `.nine-panel` 클래스가 `#ixHost .nine-panel{display:none}`
(1395행, v03.42부터 전 탭 CSS로 숨김)에 걸려 있어 **DOM엔 존재해도 화면엔 절대 안 보인다.**
이쪽은 CSS 은닉이라 `getElementById`/`innerHTML`로는 있는 것처럼 보이지만 `innerText`나
실제 렌더 결과로 확인하면 빠져 있다 — 9번 항목이 이미 지적한 함정(클래스 재사용 시 전역
숨김 규칙 확인)과 근본적으로 같은 종류다.

**실제로 화면에 남아 있던 진짜 문제는 따로 있었다** — "190만 일시납 — 종료 안내 스케줄" 표
아래 있던 "세무회계 셈" 특정 사무소 안내 문구(`<div class="notebox warn">...세무회계 셈...`)는
`stdCards`/`nine-panel`과 무관하게 **항상 화면에 그대로 노출되고 있었다.** `A.일시납스케줄`이
20번 항목 이후로 항상 빈 배열이라 스케줄 표 자체는 비어 있는데도, 그 밑의 안내 문구는 표
내용과 무관하게 무조건 떠 있어 "존재하지 않는 스케줄 행에 대한 안내"가 계속 보이는
상태였다. 이번에 `sched`가 실제로 있을 때만 이 블록이 뜨도록 고쳤다(index.html v08.214) —
**이게 이번에 유일하게 사용자에게 실제로 보이는 화면을 바꾼 수정**이다.

**이후로 지킬 것**
- **"업로드 안 하면 이 값이 뜬다"는 문장은 Playwright로 그 화면을 실제로 띄워 확인하기
  전에는 쓰지 않는다.** 소스에서 하드코딩값을 찾았어도, 그 값을 만드는 함수가 조기 `return`
  으로 비활성화돼 있거나(`stdCards()`) 그 출력 클래스가 CSS로 전역 숨김돼 있을 수 있다
  (`.nine-panel`) — 둘 다 이 파일에 실제로 있는 패턴이다(1번·9번 항목과 같은 함정의 변주).
- 화면 관련 질문에 답하기 전, 특히 "카드"·"인사이트 패널"처럼 이 파일에서 **이미 한 번
  전 탭에서 꺼진 이력이 있는 공용 컴포넌트**(stdCards·ninePanel·stepBar 등, 주석에
  "전 탭 제거"·"전 탭 숨김"이라 적힌 것들)를 다룰 때는, 그 컴포넌트 함수 맨 앞줄부터
  확인한다 — 얼리 리턴 한 줄이 그 아래 수백 줄을 통째로 죽은 코드로 만든다.
- 소스만 보고 쓴 확인되지 않은 주장은, 나중에 실제로 고치려고 화면을 띄워봤을 때 틀린 것으로
  드러날 수 있다 — 이번처럼 뒤늦게라도 정정하고 CLAUDE.md에 남긴다(2번 규칙 "확인 필요"
  원칙을 어긴 사례를 스스로 다시 정정한 것).

### 27. 26번의 "진짜 노출 버그"도 실은 오판이었다 — Playwright `.click()`은 CSS로 숨긴 요소도 눌러 버린다 (2026-09-03)

26번에서 "신청관리 > 활성화 모니터링 탭이 세무사무소목록 업로드 없이도 PAY.monStat 리터럴을
그대로 노출하는 진짜 버그를 찾아 고쳤다"고 보고했다. 그런데 사용자가 바로 다음 턴에
"신청관리-활성화 모니터링탭이 지금 없고, 컨설팅/온보딩/활성화탭은 모두 제거된 상태"라고
알려줘 다시 확인한 결과, **이것도 오판이었다** — 25번에서 "소스에 하드코딩값이 있다 = 화면에
노출된다가 아니다"라고 정리해 놓고, 바로 다음 항목에서 같은 함정에 또 걸린 것이다.

**원인** — `#ixHost .hdr,#ixHost .tabwrap{display:none!important}`(905행)로, `join`/`onb`/
`use`/`voc` 화면이 걸려 있던 레거시 내부 탭바(`.tabwrap`이 감싸는 `#tabs`, TABS 배열 전체를
렌더링하는 원본 index.html의 탭 스트립)가 `#ixHost` 안에서는 **통째로 전역 숨김**돼 있었다.
NAV(사이드바)는 이미 v07.88에서 이 4개를 뺀 상태였고(11233행 주석), 그 대체 진입 경로로
쓸 수 있다고 생각했던 이 내부 탭바 자체도 CSS로 안 보이니, **사용자 입장에서는 이 4개
화면에 도달할 방법이 아예 없었다** — 18번·23번 항목과 완전히 같은 유형("메뉴에서 뺐지만
코드는 남아있다"가 아니라 이번엔 "코드도 렌더도 되지만 그 진입 버튼 자체가 안 보인다")이다.

26번을 쓸 때 검증에 쓴 방법이 이 함정을 못 걸렀다 — `page.evaluate(() => btn.click())`처럼
**JS에서 직접 `.click()`을 호출**하면, 그 요소가 `display:none`으로 숨겨져 있어도 클릭
이벤트가 그대로 발생하고 연결된 로직이 실행된다(네이티브 DOM `click()`은 CSS 가시성을
따지지 않는다). 그래서 "버튼을 눌렀더니 `use` 섹션이 `display:block`으로 바뀌고 리터럴
값이 보였다"는 관찰 자체는 사실이었지만, **그 버튼을 누르는 행위 자체를 실제 사용자는 할
수 없었다** — Playwright의 `locator.click()`(액셔너빌리티 검사를 거치는 정식 클릭)이었다면
그 버튼이 안 보인다는 이유로 애초에 실패했을 것이다.

**처리 (사용자 확정 "완전히 삭제해", index.html v08.216)**
- 삭제한 것: join(컨설팅·가입)·onb(온보딩)·use(활성화 모니터링)·voc(문의 상담·VOC) 4개
  화면의 렌더 IIFE 전체(원래 6~9번 섹션, 약 480줄) + `TABS`·`STUB`·`IX_TABS`·`BUILT_TABS`
  배열의 해당 4개 항목 + NAV의 관련 주석 갱신(v07.88 "메뉴에서만 뺀다" → "코드까지 완전
  삭제"로 사실 정정).
- 옮겨서 보존한 것: `monData()`·`window.useRiskStat`. `use` IIFE 안에 정의돼 있었지만, 이
  둘은 **주간회의(`week`) 화면**의 "UX 자동 연동" 카드("활성화 모니터링 위험")가 여전히
  호출한다 — 화면은 죽었어도 그 값을 참조하는 다른 살아있는 화면이 있었다(21번 항목이
  지적한 "카드가 다른 화면의 함수를 그대로 가져다 쓰는" 유형과 비슷). 4742행 부근(
  `createUseFromOnb` 정의 바로 뒤)으로 옮겨 그대로 동작하도록 했다.
- 같이 정리한 죽은 링크: 주간회의 화면의 "활성화 모니터링 위험"·"온보딩 활성화 완료" 카드가
  갖고 있던 `onclick="gotoTab('use'/'onb')"`(화면이 없어져 눌러도 아무 반응 없는 죽은 클릭이
  됨) 제거, "VOC·고객센터" 섹션의 "문의 상담·VOC 탭" 링크(`gotoTab('voc')`)도 제거하고
  일반 텍스트로 바꿨다. `gotoTab()`은 대상 버튼이 없으면 조용히 무시하는 가드가 있어 에러는
  안 났지만, 눌러도 반응 없는 카드를 그대로 두는 것도 사용자 경험상 방치였다.
- 의도적으로 손대지 않은 것: `createOnbFromCons()`·`createUseFromOnb()`(4725·4735행)는 이
  화면들을 지우면서 유일한 호출처(join/onb 블록)가 같이 사라져 이제 완전히 죽은 함수가
  됐지만, 이번 요청은 "화면 삭제"였지 "죽은 코드 전수 정리"가 아니라 남겨 뒀다 — 확인 필요.
  `createConsFromInq()`(4715행)도 정의만 있고 호출처가 원래부터 없었는데(이번 삭제와 무관하게
  이미 죽어 있던 코드), 역시 이번 범위 밖이라 손대지 않았다. Supabase 키 매핑(`consulting`·
  `onboarding`·`onb_manual`·`onb_del`·`use`·`mon_contact`·`si_metric`)도 23번 항목과 같은
  이유(과거 데이터 보존)로 그대로 뒀다.
- 검증: `new Function()` 문법 통과(6블록) + Playwright NAV 17개 탭 전부 `goTab()` 이동 후
  `pageerror` 0건(네트워크 차단 잡음 제외) + `#s-join`/`#s-onb`/`#s-use`/`#s-voc`가 전부
  `null`이 됐음을 확인 + `STUB`/`IX_TABS`/`BUILT_TABS`에 4개 id가 안 남아 있음을 확인 +
  `window.useRiskStat()`이 삭제 후에도 정상값(총 392·위험 0·0)을 반환함을 확인 + 주간회의
  화면에서 두 카드의 `onclick` 속성이 사라졌음을 확인.

**이후로 지킬 것**
- **"화면에 실제로 보이는지"를 Playwright로 확인할 때, 대상 요소 자신의 `display`만 보지
  말고 그 요소를 누르기 위해 거쳐야 하는 모든 조상 요소의 가시성도 같이 확인한다.** 특히
  `btn.click()`처럼 요소를 직접 집어 호출하는 방식은 CSS로 숨겨진 버튼도 눌러 버린다 —
  가능하면 Playwright의 액셔너빌리티 검사를 거치는 클릭(`locator.click()`, 안 보이면
  타임아웃으로 실패)을 쓰거나, 최소한 그 버튼과 조상 요소 전체의 `getComputedStyle().display`
  를 눌러보기 **전에** 확인한다.
- 사용자가 "그 화면 지금 없다"처럼 내가 방금 보고한 것과 반대되는 사실을 알려주면, 방어적으로
  반박하지 말고 **즉시 같은 방법론적 의심(이번 것도 클릭 방식이 잘못된 건 아닌가)부터
  건다** — 이번에도 사용자 말이 맞았다.
- 이 프로젝트에서 "메뉴에서 뺀 화면"·"소스엔 있지만 화면엔 안 뜨는 값" 종류의 오판이 이제
  1·9·18·23·25·26·27번, 총 일곱 번 나왔다. 이 파일을 만지는 다음 세션은 **"코드에 보인다"를
  근거로 사용자에게 어떤 확정적 진술("노출된다"/"보인다"/"작동한다")도 하기 전에, 반드시
  실제 사용자 진입 경로(NAV 클릭 → 필요하면 그 안의 서브탭 클릭)로 화면을 띄워 본 결과만
  근거로 삼는다** — 소스 읽기, `getElementById` 존재 확인, `innerText` 추출, 심지어
  `btn.click()` 호출조차도 전부 "실제로 사용자가 볼 수 있다"를 증명하지 못한다.

### 28. "고객마스터 미매칭"이 전 업체에 뜬 원인 — 매칭 대상이 갱신 안 되는 정적 스냅샷이었다 (2026-09-03)

Claude 실수는 아니고, 사용자가 실제 배포 화면 캡처를 보내 "프로모션 종료·정상가 전환 탭
데이터가 하드코딩된 것 같다"고 신고해 확인·수정한 결과다. 처음엔 25~27번 교훈대로 빈 상태에서
Playwright로 직접 띄워 확인했는데 하드코딩 숫자가 안 보여 "문제 없다"고 답했으나, 사용자가
"프로모션 코드 적용 전체 현황" 표에서 **모든 업체명 옆에 "고객마스터 미매칭" 배지가 붙어있는**
캡처를 보내와 재조사했다.

**원인** — 이 배지는 `billRecs()`(4499행)가 청구 파일의 업체를 `PAY.cust`(파일 상단 리터럴
객체 안의 고정 배열)와 이름 대조해서 매기는데, `PAY.cust`는 **어떤 업로드로도 갱신되는 경로가
없는 정적 스냅샷**이다("고객마스터"라는 별도 파일을 올리는 업로드 기능 자체가 이 파일에 없음
— `grep`으로 `xlParseCust`/`__xlCust` 등 전무 확인). 그래서 청구 파일을 아무리 최신으로
올려도 대조 대상(`PAY.cust`)이 그 시점의 실제 고객과 절대 일치할 수 없어 **모든 업체가
무조건 "미매칭"**으로 뜨는 구조였다 — 하드코딩된 숫자가 노출된 건 아니지만, 실질적으로는
"업로드해도 항상 똑같이 틀리게 나오는" 하드코딩성 결함이었다.

**수정 (index.html v08.217)** — `billRecs()`의 매칭 대상을 `PAY.cust` → 실제 업로드되는
`window.__xlOfficeRows`(세무사무소목록)로 교체. 이 파일에 이미 있던 원칙(v04.94, "사업자번호
매칭이 사무소명보다 정확하다")과 동일하게 **사업자번호(byBiz 키) 우선 대조, 없으면 사무소명
보조 대조**로 구현했다(정규화 함수는 기존 `xlBizKey()`를 그대로 재사용해 청구 파일 쪽 키와
표기 방식이 어긋나지 않게 함).

**검증** — 가짜 세무사무소목록·청구 데이터를 실제로 주입해 "사업자번호가 일치하는 업체는
배지 없음, 일치하지 않는 업체만 배지 표시"가 되는 것을 Playwright로 직접 확인(소스 읽기만으로
끝내지 않음 — 25~27번 원칙 적용). 17개 탭 전수 이동 후 오류 0건.

**이후로 지킬 것**
- **"카드/표에 뭔가가 항상 같은 값으로만 뜬다"는 신고는, 그 값이 잘못된 게 아니라 "대조
  대상 자체가 절대 갱신되지 않는 정적 값"일 가능성부터 의심한다.** 이번 것도 대조 로직은
  매번 정상 실행됐지만, 비교 대상(`PAY.cust`)이 죽어 있어 결과가 항상 같았다 — 겉보기엔
  "매번 다시 계산되니 하드코딩이 아니다"로 보이기 쉬운 함정이다.
- **PAY 객체의 하위 필드를 매칭·대조 용도로 쓰기 전에, 그 필드를 갱신하는 업로드 파서가
  실제로 존재하는지(`grep`으로 그 필드명을 쓰는 `xlParse*`/업로드 함수가 있는지) 먼저
  확인한다.** 17번·21번 항목이 이미 지적한 "PAY 객체 하위 필드 중 실데이터 파이프라인이
  없는 것들"의 목록에 `PAY.cust` 기반 고객마스터 매칭도 추가된 사례다.
- 빈 상태(무업로드) 확인만으로 "하드코딩 없음"이라 답하지 않는다 — 이번 문제는 **실제
  데이터를 넣어야만** 드러났다(빈 상태에선 애초에 표에 행이 0건이라 미매칭 배지 자체가
  안 보였다). 사용자가 실 서비스 캡처로 알려준 것처럼, 데이터가 있는 상태의 화면도 함께
  고려한다.

### 29. "팀 3대 목표" 기능 추가 — 새 저장 종류 추가 시 손대야 하는 지점이 5곳이다 (2026-09-03)

Claude 실수는 아니고, 사용자 요청(대시보드 3대 목표를 팀원 활동계획과 연결)으로 새 기능을
넣으면서 확인한 사실을 정리한다. 다음에 새 데이터 종류(팀원이 입력·기록하는 값)를 저장
대상에 추가할 때 참고한다.

**이번에 만든 것** — 주간회의 화면 최상단에 "★ 팀 3대 목표" 섹션(index.html v08.218).
① 플러스전환(기존 WKKPI 재사용) ② 개업성장패키지 가입(목표 직접 입력 + 실적 자동 집계)
③ 정지·해지 윈백영업(세무사무소목록에서 대상 자동 생성 + 팀원이 업체별 처리 상태 기록).

**새 저장 종류(`board_winback`)를 추가하려면 다음 5곳을 전부 고쳐야 한다** — 한 곳이라도
빠지면 "화면엔 보이는데 저장/복원이 안 되는" 상태가 된다(8번 항목과 같은 유형의 함정).
1. `BOARD_STATE_MAP` — Supabase의 `kind` 문자열 ↔ 실제 변수명 매핑.
2. `loadFromSupabase()`의 if/else 체인 — 서버에서 읽어온 값을 그 변수에 실제로 채워 넣는
   부분(1번에 등록만 하고 여기를 빼먹으면 `kinds` 조회에는 걸리지만 화면 전역 상태에
   반영되지 않는다).
3. `MERGEABLE_KINDS` — get/set/merge 함수. 배열이고 각 항목에 안정적인 id(이번엔 사업자번호)가
   있으면 CARDS/UNIS와 똑같이 `mergeSet(...,x=>x.id)`를 그대로 재사용할 수 있다.
4. `saveToSheet()`의 `theirs` 기본값 분기 — 서버에 아직 그 kind가 한 번도 저장된 적 없을 때
   기본값을 배열(`[]`)로 줄지 객체(`{}`)로 줄지 여기서 정한다. 이걸 안 맞추면 첫 저장 시
   병합 함수가 객체 대 배열을 비교하다 깨진다.
5. `schedulePersist()`의 `P` 배열과 `__markBaselineOnly()`의 목록 — 실제로 "언제 저장을
   시도할지"와 "로드 직후 기준선을 뭘로 잡을지"를 정하는 곳. 여기 빠지면 1~4를 다 갖춰도
   저장이 나가지 않는다.

**동시 편집 위험 판단 기준(CLAUDE.md 3번 항목 재확인)** — 여러 사람이 동시에 서로 다른
"항목"(이번엔 업체)을 고칠 가능성이 있으면 반드시 `board_cards`/`board_unis`처럼 id 기반
3자 병합(`board_winback`도 이렇게 만들었다)으로 만든다. 반대로 "이번 주 목표 숫자 하나"처럼
한 사람이 대표로 입력하고 동시 충돌 가능성이 낮은 값은, 이미 있는 `board_week`(WEEKDATA,
아직 병합 안 됨) 방식에 얹어도 기존 위험 수준을 넘기지 않는다 — 다만 이것도 "여러 명이
같은 주의 목표를 동시에 고칠 수 있다"는 전제가 생기면 재검토해야 한다.

**이번 세션에서 검증한 것과 못 한 것**
- Playwright로 가짜 세무사무소목록·청구 데이터를 주입해 목표 입력→실적 자동계산→달성률
  표시, 윈백 대상 자동 생성→상태 변경→목록/상단 요약 카운트 동시 갱신까지 전체 흐름이
  실제로 동작하는 것을 확인했다(11번 항목 원칙 — 문법 검사만으로 끝내지 않음).
- **Supabase 실제 저장·복원은 검증하지 못했다** — 이 세션에는 로그인 가능한 실 Supabase
  연결이 없다(15번 항목과 같은 한계). 위 5곳을 기존 5종(CARDS 등)과 완전히 같은 패턴으로
  맞췄으므로 동작할 것으로 보이지만, 실제 서비스에서 ① 새로고침 후에도 목표·윈백 상태가
  남아있는지 ② 두 사람이 동시에 다른 업체 상태를 바꿔도 서로 지우지 않는지는 사용자가
  실제 환경에서 확인해야 한다.

### 30. 「정지·해지 제외」 필터가 걸린 원천 맵을, 상태와 무관하게 세야 하는 실적 집계에 재사용했다 — 같은 함정이 세 번째 (2026-09-06)

`xlParseBilling`은 `byBiz`/`byName`(청구 상태 관련 화면용 — 정지·해지 제외, "지금 청구 중인
곳"만) 말고도, "청구대상 확인" 탭·`pkgJoinCountRange`를 위해 `__billAllRows`(파일 전체, 상태
무관)를 이미 따로 담아 둔다(28·29번과 이어지는 v08.228/233/235 수정). 그런데 실적 분석·실적
관리 화면의 대표 카드("플러스 가입"·"플러스 전환"의 "개업성장패키지 N건 포함" 소계)가 쓰는
`perfStat()` 안의 `pkgOf()`는 여전히 `window.__billByBiz`/`__billByName`(정지·해지 제외)로
프로모션 여부를 판정하고 있었다 — 세무사무소 상태가 정지·해지로 바뀐 곳은 실제로 프로모션
대상이어도 "프로모션 아님"으로 잘못 판정됐다.

**발견 경위**: 사용자가 세 화면 스크린샷(통합현황·주간회의·누적)을 나란히 보내며
"플러스 가입수 전환수 개업성장패키지수 점검" 요청. 누적 화면의 "플러스 가입" 카드는
"개업성장패키지 6건 포함"이라 적혀 있는데, 같은 누적 화면 바로 옆 "개업성장패키지 가입"
카드(별도 계산인 `pkgJoinCountRange`, 이미 올바른 `__billAllRows` 기준)는 12건이었다 — 같은
화면·같은 시점 기준인데 6 vs 12로 갈리는 게 이상해 원인을 추적했다. 실제 업로드 파일(883행)로
직접 계산해 확인: `__billByBiz`(live)로는 프로모션 대상 6건, `__billAllByBiz`(전체)로는 13건 —
6건이 바로 이 버그로 빠진 숫자였다(사용자가 앞서 "13건이야"로 이미 확정한 실제 총량과 일치).

**수정**: `xlParseBilling`에 `__billAllByBiz`/`__billAllByName`(파일 전체 기준 매칭 맵)을
새로 만들고, `pkgOf()`가 이 전체 맵을 우선 쓰도록 변경(index.html v08.247). 청구 상태 화면이
쓰는 기존 `byBiz`/`byName`(live)은 그대로 둔다 — 그쪽은 의도적으로 "정지·해지 제외"가 맞다.

**교훈(핵심 규칙 2번 섹션 12항으로 신설)**: "정지·해지 제외" 필터가 걸린 원천은 화면 성격에
따라 맞을 수도, 틀릴 수도 있다. **통합현황(홈)은 "지금 정상인 곳"이 기준이 맞고, 실적현황
(실적 분석·실적 관리)은 "정상 여부와 무관하게 그 기간에 일어난 일"이 기준이다.** 새 계산을
만들 때 어느 화면에 쓰이는지부터 확인하고, 그에 맞는 원천 맵(`byBiz`/`byName` vs
`__billAllByBiz`/`__billAllByName`/`__billAllRows`)을 골라야 한다 — 같은 종류의 실수가
v08.228(청구대상 확인 탭)·v08.233(pkgJoinCountRange)에 이어 이번이 세 번째다.
