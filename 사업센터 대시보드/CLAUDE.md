## 2. 핵심 규칙

1. 제공되지 않은 사실·숫자·정책·데이터는 추측하지 않는다.
2. 확인되지 않은 내용은 반드시 '확인 필요'로 표시한다.
3. 사용자가 제공한 자료와 기존 파일을 최우선 기준으로 사용한다.
4. 기존 작업물이 있으면 전체를 새로 만들지 말고 기존 구조를 유지하면서 필요한 부분만 수정한다.
5. 요청하지 않은 기능이나 내용을 임의로 추가하지 않는다.
6. 결과물을 만들기 전에 요구사항 사이의 충돌·누락·중복을 먼저 내부적으로 점검한다.
7. 사고 과정이나 장황한 설명은 출력하지 않고 최종 결과와 핵심 근거만 보여준다.
8. 중요한 결정은 긴급도·고객 영향도·매출 영향도·운영 위험도 기준으로 우선순위를 정한다.
9. 부족한 정보가 있어도 작업을 중단하지 말고 가능한 범위까지 완성한 뒤 '확인 필요 사항'을 별도 표시한다.
10. 같은 내용을 여러 형태로 반복하지 않는다.
11. **(2026-09-03 확정) 모든 데이터값은 없으면 없는대로 표시한다 — 데이터는 하드코딩하지 않는다.**
    업로드·연동 데이터가 없을 때는 `null`/`'—'`/"데이터 없음"으로 정직하게 보여주고, 근거 없는
    추정치·과거 조사 시점의 스냅샷 숫자·특정 사례를 일반화한 문구를 대체값으로 채워 넣지 않는다.
    화면을 새로 만들거나 고칠 때마다 이 원칙을 기본값으로 적용한다(PROJECT_CONTEXT.md "13. 배운 점" 24·25번 항목 참고).
12. **(2026-09-06 확정) 화면 성격에 따라 "정상 상태 필터 여부"가 다르다 — 헷갈리지 말 것.**

## 4. 화면설계 규칙

화면·대시보드 설계 시 다음 항목 누락 금지:

- 화면 목적 / 주요 사용자 / 핵심 사용자 행동
- 화면 구조와 정보 우선순위
- 필요한 데이터 필드 / 데이터 산출 기준
- 버튼 및 인터랙션 / 필터와 검색 조건
- 정상 상태 / 데이터 없음 상태 / 오류 상태
- 권한별 노출 차이
- 기존 화면과 연결되는 흐름
- 개발 시 확인이 필요한 사항

구현 요청이 아니면 먼저 화면설계서·구조안을 작성하고 임의로 구현하지 않는다.

## 5. 데이터 분석 규칙

작성 순서: 데이터 정의 → 지표 산식 → 현재 수치 → 비교 기준 → 이상 징후 → 원인 가설 → 확인해야 할 추가 데이터 → 실무 인사이트 → 권장 액션 → 긴급도 및 우선순위.

데이터가 없는 경우 임의의 예시 숫자를 실제 데이터처럼 사용하지 않는다.

## 8. 사업센터 대시보드 작업 규칙

1. 요청과 기존 정책이 충돌하면 요청을 따르되, 충돌 사실을 먼저 말한다.
2. 고치기 전에 그 함수가 어디서 호출되는지 grep으로 센다 (정의만 있으면 죽은 코드).
3. 고친 뒤 페이지를 실제로 띄워 오류 확인 — 문법 검사만으로 배포 금지.
4. 카드·표 안에 설명 문장 금지. 라벨·값·증감만.
5. 입력 칸의 change 핸들러에서 그 영역을 다시 그리지 않는다.
6. 같은 유형을 고칠 때 파일 전체에서 그 패턴을 찾는다.
7. **코드/대시보드 파일을 수정하기 전에, 그 파일이 현재 최신본인지부터 확인한다** — 관련 SKILL.md·프로젝트 지침에 "원본/최신 파일" 언급이 있는지 먼저 확인하고, 파일 안의 버전 번호가 최근 대화·사용자 언급과 맞는지 대조한다. 불일치하면 작업을 진행하기 전에 사용자에게 먼저 확인한다.
8. **수정이 필요한 곳만 찾아서 최소 범위로 읽는다** — grep으로 정확한 줄 위치·호출 경로(예: goTab/RENDER 연결)를 먼저 특정한 뒤, 그 위치에 딱 필요한 범위만 연다. "구조 파악"을 이유로 관련 있을 만한 곳까지 미리 넓게 읽지 않는다. 같은 화면 이름이 서로 다른 렌더링 시스템에 중복 구현된 경우에도, 먼저 좁은 범위에서 실제 호출 경로를 grep으로 확정한 뒤 그 경로만 연다.
9. **"업로드 안 하면 이 값이 화면에 뜬다"는 주장은 소스 코드만 보고 하지 않는다** — 그 값을 만드는 함수(`stdCards()` 등)가 상위에서 통째로 비활성화(`return ''` 같은 이른 반환)돼 있거나, 그 출력을 담는 클래스가 CSS로 전역 숨김(`display:none`) 처리돼 있을 수 있다(PROJECT_CONTEXT.md "13. 배운 점" 25번 항목). 실제로 화면에 보이는지 Playwright로 확인한 뒤에만 "하드코딩값이 노출된다"고 보고한다.
10. **(2026-09-08 확정, 사용자 요청 — "수정할때마다 시간이 오래걸리는 이유"에 대해 "수정 규모별로 검증 수준을 다르게 하겠다"고 답한 뒤 "그렇게해"로 승인)** 수정 규모에 따라 검증 수준을 다르게 가져간다 — 매번 17개 탭 전수 회귀·실제 PDF 생성까지 하면 사소한 수정도 오래 걸린다.
    - **작은 수정**(문구·라벨·색상·배지 조건·숫자 하나처럼 영향 범위가 한 화면·한 조건문으로 뚜렷한 경우): 그 화면만 Playwright로 띄워 눈으로 확인. 17개 탭 전수 재확인은 생략해도 된다.
    - **큰 수정**(여러 화면이 공유하는 함수·전역 상태·저장/복원 구조를 건드리거나 영향 범위가 불분명한 경우, 데이터 산식·정합성 관련): 지금까지 해온 대로 17개 탭+week 전수 회귀, 필요하면 실제 PDF 생성·PyMuPDF 렌더링까지 전체 검증을 유지한다.
    - 작은 수정인지 애매하면 큰 수정 쪽으로 분류한다 — `main`에 즉시 자동 배포되는 환경이라(1번 섹션 참고) 검증을 놓치는 비용이 시간을 아끼는 이득보다 크다.
11. **(2026-09-08 신설, 사용자 요청 — "index파일에서 고칠위치 찾는걸 쉽게 하려면") 코드를 고치기 전에 `CODE_MAP.md`부터 확인한다** — 어떤 화면이 IX 시스템/영업 어댑터/단순 화면 중 어느 방식이고 실제 담당 함수가 무엇인지 정리해 둔 지도다(2번 항목의 grep 확인을 대신하지는 않는다 — 지도가 틀렸을 수 있으니 grep으로 최종 확인은 그대로 한다).
    - **(2026-09-08 확정, 사용자 지시)** **코드를 수정하거나 화면·함수를 추가·삭제했으면 `CODE_MAP.md`도 반드시 갱신한다.** 예외를 임의로 판단하지 않는다 — 안 갱신하면 다음에 더 헷갈리게 만드는 낡은 지도가 된다.
12. **(2026-09-09 신설 — 실수 재발 방지, PROJECT_CONTEXT.md "13. 배운 점" 37번 항목)** **사용자에게 선택을 물어보기 전에, 그 선택지가 실제로 화면에 존재하는지 확인한다.** 같은 문구·같은 화면 이름이 여러 곳에서 grep되면 어느 쪽이 실제로 보이는 화면인지 Playwright로 확인한다(`display:none`·`offsetParent`). 숨겨진 옛 화면(죽은 코드)을 근거로 "이쪽도 바꿀까요?"라고 묻지 않는다 — 없는 기능을 있는 것처럼 설명하게 되고, 사용자가 하지 않아도 되는 판단을 하게 만든다.

22. **(2026-09-23 신설 — 사용자 지적 "증감 요구사항 반영안됐는데?")** **「앞으로 쌓이는 데이터부터 적용됩니다」로 끝내지 않는다.** 사용자가 원한 것은 **지금 화면에서 보이는 것**이다.
    - **사고**: v08.350에서 스냅샷 적립 규칙만 고치고 "이미 쌓인 칸은 그대로 남고 다음 업로드부터 적용된다"고 안내했다. 배포 후에도 옛 기록 때문에 증감이 계속 0으로 보여 사용자가 같은 지적을 다시 했다.
    - **규칙**: 저장 규칙을 고칠 때는 **이미 쌓인 데이터에서도 요청이 보이는지** 반드시 확인한다. 안 보이면 **읽는 쪽(표시 로직)도 함께 고친다** — 옛 데이터를 지우거나 사용자가 기다리게 하지 않는다.
    - 검증은 **사용자 화면과 같은 기존 데이터를 심어** 확인한다(빈 상태에서만 테스트하면 이 유형을 놓친다).

21. **(2026-09-23 신설 — 사용자 지시 "목표 바꾸라는 얘기 더이상 하지마")** **목표값(연간·월 목표)은 사용자가 정한다. 바꾸라고 제안하지 않는다.**
    - 집계 기준이 바뀌어 달성률이 크게 흔들려도 **그것은 보고 대상이 아니다.** 목표는 사업 판단이지 데이터 정합 문제가 아니다.
    - 실적 숫자가 맞는지만 확인해 보고하고, **목표·달성률에 대한 의견은 붙이지 않는다**(사용자가 먼저 물으면 그때만).
    - 표의 목표 칸은 사용자가 직접 입력하는 자리다 — 내가 값을 채우거나 바꾸지 않는다.

20. **(2026-09-23 신설 — 사용자 지적 "이 숫자는 왜 이러는거야")** **집계 정의를 바꾸면, 그 값에 기대던 다른 화면의 문구·비율 바·라벨까지 함께 점검한다.** 숫자만 고치면 **설명이 거짓말이 된다.**
    - **사고**: v08.358에서 「플러스 가입」을 신규+재가입으로 좁혔더니, v08.307이 만든 포함 비율 바가 「플러스 가입 27건 안에 개업세무사 16건 포함」이라고 계속 찍었다. 실제 겹침은 4건이고, **7월은 플러스 가입 0인데 개업세무사 5**라 「0건 안에 5건 포함」이라는 문장이 화면에 떴다.
    - **규칙**: 집계 함수(`joinSplitCount` 등)의 정의를 바꾸면 **그 kind를 부르는 모든 자리**를 grep으로 훑고, 그중 **「포함」·「같은 값」·「A 중 B」 같은 관계를 단언하는 문구**가 있으면 그 관계가 아직 성립하는지 **데이터로 확인**한다.
    - 관계가 깨졌으면 문구를 지우지 말고 **실제 관계(교집합·차집합)를 세어 그대로 적는다** — 지어내지 않는다.

19. **(2026-09-23 신설 — 사용자 지적 "이건 왜 수정이 안된거야?")** **사용자가 화면의 숫자를 짚어 「이게 맞다」고 말하면 그것은 집계 변경 요청이다.** 확인 질문으로 대신하지 않는다.
    - **사고**: 사용자가 "플러스 신규1건이고 4건이 전환이잖아"라고 했는데, 나는 월별 표를 보여주며 **라벨을 나눌지만** 되물었다. 실제 집계는 그대로 뒀고, 몇 턴 뒤 "플러스 가입 1건이잖아 / 이건 왜 수정이 안된거야?"라는 지적을 받았다.
    - **규칙**: 숫자를 짚은 말에는 ① 그 숫자가 되도록 **집계를 고치고** ② 그로 인해 **빠지는 값이 어디로 가는지**를 함께 보고한다. 되물어야 할 것이 있으면 **고친 뒤에** 덧붙인다(작업을 멈추고 묻지 않는다).
    - 예외: 고치면 **다른 확정 정책과 충돌**하는 경우에만 먼저 확인한다(13번 항목).

18. **(2026-09-23 신설 — 같은 실수 2회 반복)** **문서 갱신과 커밋을 한 줄로 이어 붙이지 않는다.** 문서 스크립트가 예외로 멈춰도 뒤따르는 `git commit`이 그대로 실행돼 **코드만 커밋되고 문서가 빠지는** 일이 2026-09-20·09-23 두 번 있었다. **문서 갱신이 성공한 것을 확인한 뒤에 커밋한다**(스크립트 끝에서 바뀐 파일을 확인하거나, 커밋을 별도 명령으로 분리한다).

17. **(2026-09-16, 사용자 지시 "요구는 지키되 더나은 방법이 있다면 제안해")** — **저장소 루트 `CLAUDE.md` 5번 섹션**이 이 원칙을 이미 담고 있어(요청 방식 / 대안 / 차이 / 추천 / 이유) 여기서는 **다시 쓰지 않는다.** 사용자 확인: "중복이라면 생략해도돼". 요청은 그대로 해 놓고, 더 나은 방법은 보고 끝에 짧게 한 번만 덧붙인다.

16. **(2026-09-16 신설, 사용자 지시 — 실제 사고)** **「배포해」는 그때 그 요청 묶음에만 유효하다. 상시 승인으로 해석하지 않는다.**
    - **사고**: 사용자가 앞서 말한 "명령이 모두 수행되면 배포해줘"를 내가 **이번 세션 전체에 걸친 승인**으로 넓혀 잡고, v08.337·v08.338을 **묻지 않고 `main`에 병합·배포**했다. 사용자 지적 — "내가 배포하라고 안했는데 왜 자동 배포했어?"
    - **규칙**: 작업이 끝나면 **작업 브랜치에만 커밋하고 멈춘다.** 그 요청에 대해 사용자가 직접 "배포해"라고 말한 경우에만 `main`에 병합한다.
    - "수행되면 배포해줘"처럼 **조건을 단 말도 그 묶음 한 번**에만 적용한다. 다음 요청에는 다시 확인받는다.
    - 되돌리는 것(revert)도 배포다 — 마찬가지로 먼저 확인받는다.
    - 사용자가 배포를 원할 것 같아도 **내가 대신 판단하지 않는다**(16번 섹션의 대원칙).

15. **(2026-09-16 신설 — 실수 재발 방지, PROJECT_CONTEXT.md v03.17)** **빈 값을 이어 붙인 문자열은 「값 없음」이 아니다.** `a+'|'+b` 같은 합성 키는 둘 다 비어도 `'|'`가 되어 **참**이다 — 「없으면 판단하지 않는다」 가드를 그 합성 값으로 세우면 영원히 걸리지 않는다(실제 사고: 새 버전 알림 띠가 헤더 없는 서버에서 구조적으로 안 뜸, v08.328에서 수정). **조각을 각각 검사한 뒤 합친다.**

14. **(2026-09-16 신설 — 실수 재발 방지, PROJECT_CONTEXT.md v03.13)** **로그인 직후에 무언가를 시작·실행하는 코드를 넣을 때는 로그인 경로가 둘이라는 것을 먼저 확인한다.**
    - ① `init()` — 페이지를 열 때 **이미 로그인돼 있던** 경우
    - ② `sb.auth.onAuthStateChange`의 로그인 분기 — **로그인 화면을 거쳐 들어온** 경우
    - 실제 사고: 새 버전 알림 띠(v08.292)가 ①에만 붙어 있어, 로그인 화면을 거쳐 들어온 창은 배포가 나도 끝까지 알림을 받지 못했다(v08.323에서 수정). 한쪽만 고치면 "어떤 사람에게는 되고 어떤 사람에게는 안 되는" 버그가 되어 재현이 어렵다.

13. **(2026-09-16 신설, 사용자 지시)** **한 번 바꿨다가 되돌린 항목은, 같은 요청이 다시 오면 먼저 그 이력을 알리고 "정말 변경할까요?"라고 확인받은 뒤에 작업한다.** 되돌린 데는 이유가 있으므로, 같은 왕복을 반복하면 배포만 흔들린다.
    - **되돌린 항목 ①: 유입경로를 신청 관리로 옮기기**(v08.318 → v08.320에서 원복).

    - 두 항목에 대한 새 요청이 오면: ① 바꿨다가 되돌린 사실과 위 근거를 먼저 말하고 ② 확인을 받은 뒤에만 다시 작업한다(확인 없이 바로 고치지 않는다).
